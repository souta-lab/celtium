# Celtium vs pinned Celeritas `989ebf2e` — steady-state performance measurement

Date: 2026-10-11. Machine: 6-core Intel i5-8400, AMD Radeon RX 6400 (Navi 24, RADV, Mesa 26.2.4-1) at
render node `renderD129`, 4 GB VRAM, headless Sway/Xwayland compositor at 1280x720@60Hz.

This is the performance measurement the objective asks for: steady-state CPU and GPU time, FPS, p95/p99
frame time, memory and chunk-update cost, for Celtium and for the pinned upstream Celeritas reference,
under the same conditions. Every number below is paired with the control that produced it. **No speed-up
is asserted anywhere in this document**; section 6 states exactly what the numbers do and do not show.

Raw, machine-generated evidence (every run, every frame array, every control read back from inside the
game): [`docs/performance-2026-10-11-evidence.md`](performance-2026-10-11-evidence.md), regenerated by

```
python3 scripts/benchmark_celtium.py --from-results .celtium-work/bench/results-20261011-091631.json
```

## 1. What the existing script and fixture already did, and what was added

The previous agent left `scripts/benchmark_celtium.py` (799 lines) and `scripts/bench-fixture/`
(a Forge mod built at run time). Examined before touching anything:

**Already there and kept**

- A measurement fixture (`BenchFixture.java`) that launches its own flat world, pins the world time,
  kills rain/thunder, pins the lightmap torch flicker, applies a frame cap and a vsync flag, and records
  raw per-frame times for a fixed frame count after a warm-up that must finish first.
- Per-run collection of process CPU jiffies (`/proc/self/stat`) and RSS/peak-RSS (`/proc/self/status`),
  the load average at both ends of the measured window, the frame cap / vsync / render distance read back
  at both ends, the camera, the world seed and the renderer's own debug strings.
- A runner that compiles and reobfuscates the fixture (MCP → SRG with a derived mapping), launches one
  game instance at a time through `scripts/prism_validation.py` into a fresh game directory (never writing
  into the Prism instance's `minecraft/mods`), alternates the configuration order between rounds, hashes
  every jar before and after each run, and computes p50/p95/p99/max with the same nearest-rank rule the
  validation fixture uses.
- A GL-less configuration was *not* among the two configured keys, so the objective's target
  configuration had never been measured.

**Broken, and fixed here**

- `BenchFixture.world()` opened the measured window with `if (measuredFrames == 0) { beginWindow(...); return; }`,
  but `beginWindow` does not increment `measuredFrames` — so every frame re-opened the window and the
  counter never advanced. The fixture could never sample a single frame. This is what killed the previous
  agent's runs (`.celtium-work/bench/runs/20261011-012423-01-celtium/`, whose console prints
  `[CeltiumBench] window open` once per frame until the run was killed). Replaced with an explicit
  `windowOpen` latch.
- `writeReport` called `glGetString` from the JVM shutdown hook, where no GL context is current; that is a
  native `FATAL ERROR ... No context is current` and it aborted the JVM instead of writing the report
  (`.celtium-work/bench/runs/20261011-012046-01-celtium/validation-console.log`). GL strings are now
  captured on the client thread when the window opens.
- The chunk phase only ended when the renderer's queue read zero, which in a scene with lava/fire never
  happens; the phase burned its 900-frame cap and wrote a `PARTIAL` report instead of the measurement.
  It now measures a fixed number of post-placement frames for every configuration and reports the
  queue-empty frame beside the samples.
- The camera was wherever vanilla's fuzzed spawn put it (`nextFloat() * 2 - 1` per axis): two runs of the
  *same jar* stood 3 blocks apart in the smoke runs. The fixture now holds a fixed pose on the client
  every tick and teleports the server-side player to it once through `EntityPlayerMP.setPositionAndUpdate`
  — the same technique `validation/client` uses — so every run stands at exactly `0.5, 12.0, 0.5,
  yaw 180, pitch 20`.
- The scene's default flat world contains lava, fire, water and leaves, which keep producing block updates:
  the chunk queue never rested (89–122 pending through the whole window in the smoke runs) and the visible
  scene drifted between runs as fire spread. The measured world is now static
  (`bedrock, 2*dirt, grass, stained_glass`), which is what makes "steady state" mean anything and what
  makes the chunk-update phase isolate the 64 placements.

**Missing from the runner, and added**

- A `celtium-glless` configuration, so the objective's target is actually measured.
- A per-configuration JVM argument list (the GL-less flag) with everything else identical.
- Jar **pinning**: each configuration's jar is copied to `.celtium-work/bench/jars/<sha256[:16]>-<name>`
  before the first run and the copy is what runs. Two other agents rebuilt the mod jar during this session;
  without pinning, round 1 and round 2 would have measured different bytes. They did anyway — see §7.
- A **control audit**: every control that must be equal (frame cap, vsync, render distance, resolution,
  seed, world layers, world time, camera pose and observed camera) is read back from inside the game and
  compared across configurations, with a verdict rather than an assumption.
- A **load gate**: runs whose window-start 1-minute load average exceeds (lowest + `--load-delta-limit`,
  default 1.0) are marked outliers, excluded from the deltas, and the offending configuration is re-run
  once automatically (`--auto-rerun`). This machine is shared with seven other agents; a benchmark without
  that context is not evidence.
- GPU-side sampling from the driver (`/sys/class/drm/renderD129/device/gpu_busy_percent`,
  `mem_info_vram_used`), sliced to the fixture's own window marks — the only GPU metric available for
  *both* the Vulkan and the OpenGL configurations, since the OpenGL reference publishes no timestamps of
  its own.
- A `--markdown` evidence document, a `--from-results` re-render mode and a `--merge-results` mode.
- Diagnostic-log volume per run (the fork prints its own counters inside the measured window; the
  reference prints none) — measured rather than asserted.

### 4.2 Every run

Seven runs were taken (two rounds of three plus one automatic re-run of a load outlier). All seven
reported `status=COMPLETE`, 900 measured frames, the same world, seed, layers, camera and controls, and a
**chunk queue of 0 at both ends of the measured window** (`queueMax` 0–2). The full table, with per-run
load averages and the external load band, is in the evidence file §"Steady state" and §"Machine load".
The four load-outlier runs are kept in the record and excluded from the deltas. What the load did is
visible in them: the GL-less runs read p50 5.12 ms at load 7.37, 3.94 ms at 3.03 and 4.30 ms at 4.77, and
the bridge read 5.03 ms at 7.42 against 4.89 ms at 2.68. The reference did not move with load at all
(16.09 ms at load 7.15 against 16.10 ms at 3.60) — one more sign that its number is a floor rather than
work.

### 4.3 Is the frame time a cost or a floor?

The runner classifies each run's frame interval from its own samples. The pinned reference's 16.10 ms is
**not** its render cost:

- its p50 sits within 4 % of the 16.667 ms 60 Hz interval (and inside the runner's 6 % band) with a
  p95 − p50 of 0.58 ms — a nearly constant
  interval;
- a preliminary run of the same fixture on the same scene at **render distance 8 (64 visible sections)**
  measured the reference at p50 = 16.06 ms; at render distance 12 (**147 visible sections**, +130 %) it
  measured 16.10 ms — a 0.03 ms change for 2.3× the geometry;
- its process CPU work is 3.09 ms per frame and its GPU is busy a median of **7.5 %** of the window
  (p95 19 %) — the renderer is idle most of the time it is being measured.

A frame interval that does not respond to scene complexity while both its CPU and its GPU have headroom is
a floor imposed outside the renderer (swap, compositor or limiter). **This dataset does not establish which
of those it is** — that would need a swap-interval experiment it does not contain. What it does establish
is that the reference's 16.10 ms must not be read as "the reference needs 16 ms to draw this scene".

Both Celtium configurations classify as render-cost (p50 69–76 % below the 60 Hz interval), so their frame
times are the thing the objective asked to measure. The comparison in §4.1 is therefore asymmetric, and
§6 says so.

### 4.4 CPU and memory

- **CPU work per frame** is the metric that is comparable across a capped and an uncapped configuration,
  because it counts consumed CPU rather than elapsed time: reference **3.09 ms**, GL-less **3.33 ms**
  (+8 %), GL bridge **3.94 ms** (+27 %). Per-frame CPU work is thus close to the upstream reference for
  GL-less and about a quarter higher for the GL bridge.
- **CPU seconds per measured window** are 2.78 s (reference, 14.50 s window), 3.00 s (GL-less, 3.87 s) and
  3.55 s (bridge, 4.61 s) — the reference's window is 3.7× longer, so its percentage of one core (19 %)
  looks small while the total is comparable.
- **Peak RSS** is higher for both Celtium configurations: 2368 MB (GL-less) and 2468 MB (bridge) against
  1745 MB for the reference — +36 % and +41 % on the same scene, same render distance, same JVM flags
  (`-Xms512m -Xmx2g`). This is the fork's Vulkan arenas, mirrors and atlases, not the world.
- **Log volume inside the measured window**: the Celtium build printed 14 776–25 397 `CELTIUM_*`
  diagnostic lines per run (3.7–7.8 MiB of `latest.log`); the reference printed none (265 log lines,
  0.04 MiB). That cost is inside every Celtium frame in this dataset and is a confound in Celtium's
  disfavour.

### 4.5 GPU

- The selected GPU is named from the renderer's own line, parsed out of each run's console log:

  | run | `CELTIUM_NATIVE_DEVICE` |
  | --- | --- |
  | `celtium-bridge` | `name="AMD Radeon RX 6400 (RADV NAVI24)" uuid=00000000030000000000000000000000 matchedOpenGl=true` |
  | `celtium-glless` | `name="AMD Radeon RX 6400 (RADV NAVI24)" uuid=00000000030000000000000000000000 matchedOpenGl=false` |

  `matchedOpenGl=false` under GL-less is correct and expected — there is no GL device to match under the
  stub — and the name and uuid are the same device as the bridge run. The pinned reference has no such
  line (it is upstream and does not know the token); its device evidence is its GL renderer string
  `AMD Radeon RX 6400 (radeonsi, navi24, ACO, DRM 3.64)`, GL 4.6, at 1280x720, which is the same physical
  GPU. The runner also looks for the launcher's `nativeDeviceName`/`nativeDeviceUuid`; in this dataset
  `validation-process.json` did **not** carry them (they are produced under `--validate`, which a benchmark
  run does not use), so no number here rests on them.
- The fixture's capability probe ran in every run and wrote `logs/celtium-capabilities.json`. Its
  `vulkanDevices` list is real and useful: it enumerated the RX 6400 as device type 2 (discrete) with
  device UUID `00000000030000000000000000000000`, plus an Intel UHD 630 (type 1) and llvmpipe (type 4) —
  the same uuid the bridge run's own device line reports. **Its `effectiveTerrainBackend` and
  `nativeTerrainImplemented` fields are not evidence**: `celtium-probe/src/main/java/org/soutalab/celtium/probe/ProbeReport.java:10-11`
  assigns them the constants `"opengl"` and `false`, which is why the file says `opengl` while the drawing
  renderer's own live line says `Terrain Backend: vulkan (Vulkan device matched the OpenGL device UUID and
  the interop contract was satisfied)` in every Celtium run. The live line is the backend evidence here.
- **Per-terrain-pass GPU time** (the backend's own Vulkan timestamp queries) is published only by Celtium:
  `solid 0.379–0.386 ms` and `translucent 0.655–0.658 ms` over 147 sections, in every Celtium run. The
  pinned reference publishes `?? ms` for the same passes — its OpenGL backend has no timestamp queries, so
  there is **no whole-frame GPU time for either side** and no GPU time at all for the reference. This
  document therefore does not claim a GPU-time comparison; it reports what each side publishes.
- **Driver counters** (whole GPU, includes anything else using the GPU, sampled outside the process):
  median busy 51.5–54 % (p95 56–59 %) for Celtium against 7.5 % (p95 19 %) for the reference, and VRAM
  peak 791–873 MB for all three. The reference's low busy percentage is the same fact as §4.3 seen from the
  GPU side: it is waiting, not drawing.

### 4.6 Chunk updates

The fixture places the **same 64 blocks** (2 per tick, at a fixed pattern around the camera) in every run
and then measures the next **200 frames**. The renderer's own `Chunk Queues` line is read at both ends of
the steady-state window and during the chunk phase.

| configuration | blocks placed | placement ms | queue at window start / end / max | queue empty at frame | post-placement frames p50 / p95 / p99 / max (ms) |
| --- | --- | --- | --- | --- | --- |
| `celtium-glless` | 64 (0 failures) | 3 | 0 / 0 / 1 | 5 | 5.99 / 7.46 / 13.64 / 15.18 |
| `celtium-bridge` | 64 (0 failures) | 2 | 0 / 0 / 2 | 5 | 6.85 / 8.51 / 15.76 / 19.17 |
| `reference-celeritas-989ebf2e` | 64 (0 failures) | 2 | 0 / 0 / 0 | 5 | 16.10 / 16.80 / 17.37 / 19.08 |

What is measured: the renderer's own queue depth (upload plus the three rebuild priorities, summed from
its `Chunk Queues: U=.. (P0=.. | P1=.. | P2=..)` line — the same line upstream publishes, and the fixture
reads it reflectively from both jars) and the frame times of the fixed post-placement window. All three
configurations absorbed the same 64 placements and had the queue back to zero by frame 5; in the steady
state the queue was empty at both ends of every window. The reference's post-placement frames do not move
off its 60 Hz floor (16.10 → 16.10 ms), which is the same floor as §4.3 and not evidence that its rebuild
path is free; Celtium's post-placement p50 rises from 3.94 to 5.99 ms (GL-less) and 4.89 to 6.85 ms
(bridge) — the measured cost of the same edits, at 3.7–4.3× the frame rate.

There is deliberately **no invented chunk metric** here: upload bandwidth, mesh build time and per-section
rebuild microseconds are not published by either renderer in this configuration, so they are not reported.

## 6. What the numbers do and do not show

**They do show**

1. In this scene, at render distance 12 on the RX 6400, **Celtium GL-less delivered 253.8 fps (p50 3.94 ms)**
   and **the GL bridge 204.3 fps (p50 4.89 ms)** in 900-frame windows whose chunk queue was empty at both
   ends, with all controls read back equal.
2. Per-frame CPU work in the same windows was **3.33 ms for GL-less, 3.94 ms for the bridge and 3.09 ms for
   the pinned reference** — i.e. within 8 % of upstream for GL-less and about +27 % for the bridge.
3. The pinned reference was held at the **60 Hz presentation interval** (p50 16.06 ms at 64 sections and
   16.10 ms at 147 sections, p95 − p50 ≈ 0.6 ms, GPU busy a median of 7.5 %). Its frame time is a floor
   imposed outside the renderer in this environment, not its render cost.
4. Peak RSS is **+36 % (GL-less) and +41 % (bridge)** over the reference on the same scene, and the fork
   printed 15 k–25 k diagnostic lines per run inside the measured window where the reference printed none.
5. Trailing-frame behaviour is mixed: Celtium's p99 is 2.5× lower, its single worst frame is worse
   (43.5 ms vs 18.6 ms).

**They do not show**

1. **They do not show that Celtium renders this scene 4× faster than Celeritas.** The reference never got
   to use its headroom; its frame time is a floor. The 4.09× fps ratio is a *frame-delivery* ratio under a
   floor that the reference was subject to and Celtium was not, and it is not a ratio of render costs.
2. **They do not show a GPU-time comparison.** Only Celtium publishes per-pass GPU timestamps; the OpenGL
   reference has none, and neither side publishes whole-frame GPU time. "GPU time" in this dataset means
   the per-terrain-pass numbers in §4.5 only.
3. **They do not show why the reference is floored.** Swap interval, the 60 Hz headless compositor and an
   internal limiter are all consistent with the evidence; the dataset does not distinguish them.
4. **They do not generalise beyond this scene.** One flat world with one camera, one render distance, one
   resolution, no entities, no weather, no GUI interaction, in a fresh game directory with default options.
   The heavy default world (lava, fire, water, leaves) was deliberately not used: it never lets the chunk
   queue rest, so nothing in it is steady-state, and its fire changes the scene between runs.
5. **They do not establish the GL bridge's number as a property of "Celtium".** The bridge read 4.89 ms
   on the build this section quotes and 16.09 ms on the newest build, sitting on the same 60 Hz floor as
   the reference in that run (§7); which of the two the current sources produce, and why, is not settled
   here.
6. **They are not a like-for-like comparison of the shipped mods either.** The Celtium side is a
   development build whose diagnostics run inside the measured window and which was rebuilt by other
   agents mid-session (see §7); the reference is a pinned release-lineage jar. The confounds are in
   Celtium's disfavour and are reported rather than removed.
7. **They say nothing about the Java version.** Every configuration ran the same JVM
   (Java 25, `-Xms512m -Xmx2g`, the instance's own classpath), so the difference between them cannot be a
   difference of Java or of API.
8. **They are not a substitute for the picture.** Frame times say nothing about whether the frame is
   correct; that is what the validation fixture and `scripts/compare_validation.py` are for.

Read it as follows.

- **The reference replicated exactly**: 16.099 / 16.063 / 16.06 ms in three independent runs across two
  builds and loads from 3.6 to 5.6, with a 0.5–0.6 ms p95 − p50. Nothing in the Celtium side's variability
  touches it.
- **GL-less replicated across all three builds**: p50 2.83–3.94 ms, CPU 3.3–4.6 ms/frame, at loads 3.0–7.8.
- **The GL bridge did not.** It read 4.89 ms on `d2073e94`, 6.99 ms on `f1007b13` (load 6.24) and 16.09 ms
  on `c1d4e7db` (load 4.43) — the last sitting on the same 60 Hz floor as the reference, with 5.07 ms of
  CPU per frame and a 4 % GPU busy median, i.e. working but not delivering. That run also printed **none**
  of the 19 770 `CELTIUM_MODEL_MATRIX` lines every earlier bridge run printed (its only presentation lines
  were `CELTIUM_SWAPPOINT`/`CELTIUM_PRESENT`, which all four runs have), so the native model-draw path did
  not run in it, although its live `Terrain Backend:` line still said `vulkan`.
- **This dataset does not say why.** A change in the newest build is the likely cause — these builds are
  being edited by other agents while this measurement runs — and the runs that could separate a build
  change from machine and GPU contention were not taken. The bridge number in §4.1 is therefore a property
  of jar `d2073e94`, not of "Celtium" in general, and the same applies to every number in this document.

The three datasets are **not merged**: mixing builds would break the "same jar" control that the runner
pins. Each results file carries every run's jar sha256 before and after the run and records
`jarChangedDuringRun` per run, so a jar that changed under a measurement is visible rather than averaged
away. `scripts/benchmark_celtium.py --merge-results a.json,b.json --merge-out merged.json` will combine
datasets and recompute the deltas and the load gate over the union, but it is the right tool only when the
hashes agree.
