# Celtium 0.1.3-alpha-rc.5 — NVIDIA device loss native crash containment

**Experimental test build. Windows runtime NOT verified.** Builds on RC4 (terrain visibility, model-cache recovery, Windows synchronous presenter default).

## Why this release exists

External Windows 11 / RTX 3070 tester Neeyo provided `hs_err_pid24484.log`, whose Java-to-native crash stack is:

`DynamicTexture.updateDynamicTexture → VulkanTextureRegistry.announceFullPixels → VulkanGlTexture.ensureStaging → VulkanContext.celtium$awaitDeferredSubmit → celtium$awaitDeferredEntry → celtium$reclaimDeferred → vkResetFences → nvoglv64.dll`.

On RC1, `vkQueueSubmit` had already returned `VK_ERROR_DEVICE_LOST (-4)`. Celtium nevertheless treated that result as a fully reusable submission and reset the fence through the native driver. The crash is a NULL-pointer read inside the NVIDIA DLL.

## Fixed

- **Never call `vkResetFences` or recycle deferred fences when the device is lost.** `VK_ERROR_DEVICE_LOST` now immediately latches the context unusable and raises an actionable Java exception before reclaiming any native handles.
- Detect device loss from both `vkWaitForFences` and `vkGetFenceStatus` and avoid native driver calls on that path.
- A failed asynchronous batched submission may have partially succeeded: quarantine its buffers/fence instead of freeing/recycling possibly still-in-use objects.
- Skip Vulkan-native cleanup once device loss is known, rather than risking a second access violation in an unstable driver. OS process teardown will reclaim resources.
- GPU-independent unit test ensures lost-device results can never reach the deferred fence recycling path.

## Important remaining questions

This **fixes an actual post-device-loss cleanup defect** demonstrated by the native crash trace, but the *original reason why the NVIDIA Vulkan device becomes lost is still unknown*. It may still report a Java exception or cease rendering. Compare RC5 on Windows without extra flags first (asyncPresent is disabled by default there), then with `-Dceltium.vulkan.asyncPresent=true` for A/B only if the baseline is stable. Please attach the Prism client log; never post the raw JVM crash log without first redacting its `--accessToken` argument and user identifiers.
