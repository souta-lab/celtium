# Celtium 0.2.2-rc1 — Windows entity rendering fix

*Released 2026-11-16 · tag [`v0.2.2-rc1`](https://github.com/souta-lab/celtium/releases/tag/v0.2.2-rc1) · previous [`v0.2.2`](https://github.com/souta-lab/celtium/releases/tag/v0.2.2)*

Release candidate for a single fix on the 0.2.2 line. On Windows, entity and player models drawn from client
memory silently failed to render — only the shadow appeared. This candidate fixes the readable-range guard
behind that failure. Windows real-machine verification is still pending, hence the rc.

## Fixed

- **Entity and player models render on Windows again.** The GL stub's client-pointer fault guard determined
  readable memory from `/proc/self/maps`, which exists only on Linux. On Windows the guard therefore refused
  every draw from client memory that was not covered by an owned-buffer publication, so models drawn from their
  own direct buffers (for example EfficientEntities' `ModelBiped` / `ModelPlayer` and `ModelSlime`) never
  appeared, while the shadow — drawn through the BufferBuilder path — remained.
- The guard now uses an OS-independent readable-range check (`ReadableMemoryRanges`): Linux keeps the existing
  maps parser with unchanged behavior; Windows resolves committed, readable regions via `VirtualQuery` (FFM);
  other OSes keep the previous refuse-by-default behavior. If the Windows binding fails, the guard degrades
  safely to refusal, as before. The guard's other call sites (drawElements indices/vertices, split-array
  repack) go through the same entry point and benefit identically.
- Regression tests cover the range arithmetic, the Windows protection attributes and region walking (against
  fake functions), and the stub's accept/refuse behavior. `celtium-vulkan`: 94 suites / 459 tests, 0 failures.

## Known limits

- No Windows real-machine run yet: the `VirtualQuery` FFM binding, the census reporting readable ranges, and
  actual rendering under EfficientEntities (plus frame-time impact) are unverified on hardware.
