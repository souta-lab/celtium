# Celtium 0.1.4-alpha-rc.5 — legacy immediately off (bisect build)

The tester's black screen survives rc.4. Both of their logs end the same way: a RADV
`GPUVM fault detected at address 0x800101a00000`, then `CELTIUM_VULKAN_DEVICE_LOST`,
then every present skipped (`lastSkip=[no frame target, or stalled]`) and the picture
stayed black. The fault address is identical in both runs, so it is deterministic rather
than corrupted memory. It could not be reproduced here: the same published JAR and this
build, at 854x480 and 1920x1080, under Xwayland and native Wayland, on the same instance
and mod set, present every menu frame with no device loss and no validation messages
(the menu also runs clean with the Khronos validation layer on).

The one thing that changed between the last non-crashing build and the first crashing
one is the legacy immediate path: `glBegin`/`glVertex3f`/`glTexCoord*` are routed to the
immediate pipeline so the loading screen's progress bar is drawn. In both of the tester's
logs the last submission before the fault is that quad.

This build turns those routes **off by default**. The only visible difference is that the
loading screen's progress bar is not drawn (its geometry is refused and counted like any
other unrouted call). `-Dceltium.gless.legacyImmediate=true` turns them back on for an A/B.

What to report back:
- If the black screen is gone: the legacy route is implicated and the next build fixes it
  instead of disabling it.
- If it still happens: the next bisect is the off-target window path (menu post/preview
  framebuffers). The log line to include is `CELTIUM_VULKAN_DEVICE_LOST` and anything with
  `GPUVM` around it.

Everything else is unchanged from rc.4.
