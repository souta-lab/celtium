# Celtium 0.1.4-alpha-rc.22 — a mirror is dropped only after the draws that name it

Two black-screen reports from the same machine end the same way: a mirror upload announced from the game's
own upload, then a GPUVM fault at the same address, with a GL texture deletion immediately before it. The
two reports together also retire a hypothesis: one crashed after a 256x256 announcement and one after the
4096x4224 font atlas, so size is not the variable.

What they share is ordering. A texture that is reallocated or deleted drops its mirror, and the groups
already queued against that mirror were left to resolve it at draw time - or to sample a view whose image
was being dropped. The delete path now does what the announcement path already did: if a queued group
samples the id, the pending work is drawn first, against the state it was recorded with, and only then is
the mirror forgotten.

rc.22 also carries rc.21's `CELTIUM_ANNOUNCE_EXTENT` and `CELTIUM_MIRROR_RECREATE` and rc.20's
`CELTIUM_UPLOAD_EXTENT`, so the next report says which extent was announced beside the image held, whether
the image was rebuilt, and what the copy then did.
