# Celtium 0.1.4-alpha-rc.4 — released-image guards

Follow-up to 0.1.4-alpha-rc.3 for the black screen one tester hit after the loading
screen. The renderer now refuses a draw or pass whose texture image has already been
released instead of binding the released handle.

## What was measured

The tester's log shows the sequence directly: a menu/reload phase deleted and recreated
screen-sized framebuffer textures, then wrote a descriptor; RADV reported
`GPUVM fault detected`, the context was lost, `CELTIUM_VULKAN_DEVICE_LOST` quarantined
its pending work, and every later present skipped with `lastSkip=[no frame target, or
stalled]` - a lost device has nothing left to present, so the screen stays black.

The immediate pipelines already refused a zero image view (the comment on that guard
names the same RADV device loss). The terrain pipeline and the post chain did not: they
built descriptor image infos straight from `atlas.view()` / the chain target's view.
Both now check image, view and sampler first and refuse the pass with one bounded
`CELTIUM_DEAD_TEXTURE_REFUSED owner=...` line.

## Verification

SuperSymmetry world leg with a forced resource reload at tick 400 (atlases and screen
targets recreated mid-run): zero device-loss events, zero dead-texture refusals (nothing
needed to refuse), zero refusal markers, zero validation messages, warm P50 2.57 ms.
854x480 menu leg: 2999 of 2999 presents, no device loss.

The guards did not fire in either leg, which is the expected healthy result: they are a
safety net, not a path taken by a working frame.

## Still open

If the black screen recurs on this build, the log line to report is
`CELTIUM_DEAD_TEXTURE_REFUSED` (guarded path) or `CELTIUM_VULKAN_DEVICE_LOST` (a
different path, still being chased). Reproduction details - when it happens, whether a
window resize or fullscreen toggle precedes it, which screen - are wanted.
