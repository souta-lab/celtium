# Celtium 0.1.4-alpha-rc.26 — the frame target is not rebuilt under an open recording

This is the build that actually fixes the tester's black screen. rc.24/rc.25 did not, because two wiring faults
kept the guard blind:

1. `frameBufferOpen` was declared to be "set at its begin" but only ever *cleared*; no assignment set it true, so the
   retire-drain guard never fired for the frame's own recording.
2. Even with the flag live, `ensureFrameTarget()` releases the old pair's images and framebuffer in place on a size
   change. The real launch changes size once - the window opens at 854x480, then goes fullscreen at the monitor size -
   and that change can land while the frame's unified command buffer is still recording.

The flag is now set where the frame's command buffer begins, and a size change that arrives under an open recording is
refused for that recording and retried on the next one (`CELTIUM_FRAME_TARGET_DEFERRED` names it).

## Evidence

On the tester's launch of this build: VUID 0, device loss 0, GPUVM 0, and
`CELTIUM_FRAME_TARGET_DEFERRED from=468x1018 to=1920x1080` fired twice - the deferral doing what it was written for.
Previously the same launch produced `VUID-vkEndCommandBuffer-commandBuffer-00059` (two images and a framebuffer
destroyed while bound to a recording buffer) and the black window.

Canonical plain gate: PASSED with floors enforced and the presented image judged.
Also carries rc.25's `celtium-device-lost.log` report and rc.24's retire-safety rules.

## Known open issues (fidelity, not validity)

With the black screen gone, four visual defects are visible and reproducible: main-menu background missing, tooltip
afterimage, blocks flickering / structures appearing in the sky (persist with the GUI hidden), and only some creative
inventory tabs rendering wrong. The validation layer reports no violations for them, so they are renderer fidelity
bugs, and they are the next work.
