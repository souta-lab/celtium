# Celtium 0.0.3-alpha — release draft (**NOT PUBLISHED**)

**Status: draft.** Nothing here is tagged, packaged or published yet: the tag, the artifact hash and the
`scripts/verify_forge_jar.py` run are filled in when it is, the same way `0.0.2-alpha.md` records them after the
fact. This file exists so that the two headline items the user asked the next release to carry — **HEI support**
and the **~3x faster frame path** — are held to a contract with the numbers they rest on, and so that what is
*not* in them is written down next to what is.

Baseline for every "before" number here: `v0.0.2-alpha` (`036a5d0b2`, artifact
`celtium-forge-mc1.12.2-0.0.2-alpha.jar`, SHA-256 `c2b69d03…b94471fc`, 2,594,729 bytes).

The reference is upstream Celeritas `989ebf2e` drawn through GL; the candidate is this build under GL-less. Both
legs, the instrument (`scripts/cpu-contract/font-shadow-main-check.py`, needs `--main 255,255,255 --shadow

`docs/mod-compatibility.md`.

**So "HEI support" in a 0.0.3 means**: the item list, the icons, the search/filter, the transitions and the
screen's own text are measured against the reference and match; **the vanilla tooltip text is a known, measured
defect of the shared font path, not of HEI**. If that is not acceptable for a release, the release notes must say
it in these words rather than dropping the row.

## Headline 2 — the frame path (0.0.2 → 0.0.3)

The other session's cumulative ledger (`celtium-drains/docs/perf-status.md`), on a flat world, **RX 6400 only**,
which is the range in which these numbers are measurable:

| Axis | 0.0.2 | now | Factor |
|---|---|---|---|
| Backend frame render p50 | ~9-11 ms | **3.5 ms** | ~2.5-3x |
| Frame interval p50 (vsync floor included) | ~16.7 ms | **6.9-7.1 ms** | ~2.4x |
| F3 overlay on | 43.1 ms | **13.8 ms** (four-line panel, §0.379) | ~3x |
| GUI bracket | ~2-4 ms | **0.2 ms** | — |

Three honest limits on that table, which the release notes must carry:

* It is **not** a comparison against Celeritas GL under matched conditions; that is completion condition (g) and
  is still open.
* It is **RX 6400 only**. The Intel legs of the same fixes (see below) show the same behaviour but different
  costs — the texture-copy readback, for instance, costs **~24 ms on AMD and 0.7-1.0 ms on Intel**, a 25x
  difference for the same work.
* The F3 row depends on the panel's length, which is a *display* decision (§0.379) and not a rendering win: the
  full 23 KB panel still costs 34.5 ms of `gui` time by design, behind `-Dceltium.f3.fullSummary=true`.

The units that carry the frame-path change, all landed and pushed: PRs #1-#14 — GPU waits removed from the render
thread, GUI batch matrix merging, lazy texture supply, stub dispatch without per-call allocation, the entity
gather cached at tick granularity, glyph batching per string, primitive GL state tables — plus this session's
menu-path fixes below.

## Explicitly not in a 0.0.3

* **No Intel acceptance of a release artifact.** Intel legs exist for the fixes above (dev jars); no release jar
  has been run on Intel.
* **The loading screen is still white** until §0.378 lands. The root cause is named; the fix is not in yet.
* **The vanilla tooltip's main text pass still loses 73.4% of its strokes** on the HEI screen.
* **The GL bridge (`-Dceltium.vulkan.glless=false`) still deadlocks** on the first world frame on this machine.
  GL-less is the default, so a release is not exposed to it, but it is not a working comparison arm.
* **No scanout / compositor-output proof**, no shader-pack support, no fair Celeritas-GL performance comparison,
  and the residual p99 spike remains unattributed.

## Version decision

`0.0.3-alpha` is the right number for this content: the baseline is 0.0.2-alpha, everything here is additive and
measured, and none of it claims the completion conditions the objective sets (a)-(h). Calling it 0.1.0 would
claim the shaderless body is accepted, which the "explicitly not in" list above says it is not.
