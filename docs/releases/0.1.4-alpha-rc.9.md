# Celtium 0.1.4-alpha-rc.9 — two per-window costs, and what the thermal state does

Two measured CPU costs removed, and one measurement correction that matters for every number
in this project.

## The published transition stops rebuilding its view per window

`transitionPublishedFrameTextures` runs once per window - about fifty a frame on a world
scene - and each run pruned the published set and resolved every name's image through two
maps. It now caches the resolution and rebuilds only when the publication version changes or
a chain-pair image set is created; those are the only two ways a name's meaning changes, and
the prune is what follows them.

Susy world leg: warm P50 2.73 ms (the same evening's rc.8 legs read 2.84 and 3.10), no
refusal markers, no validation messages, no device loss.

## The light cache holds one chunk rebuild

The cache is cleared on every world-time or light-map change, so its capacity is one tick's
working set. At 1,024 entries a 16^3 section rebuild (4,096 positions) exceeded it and every
eviction fell back to `World#getCombinedLight`. 8,192 entries, same-machine A/B on ATM3:
tick P50 5.68 -> 4.26 ms (-25%), frame P50 2.32 -> 2.27 ms.

## Thermal state, not the renderer, set the last ATM3 number

The ATM3 gap reported earlier (Celtium 4.35 ms against Celeritas 1.41) was measured while the
machine was thermally loaded. Measured cool on the same two arms:

| ATM3 terrain RD4 | hot | cool |
|---|---|---|
| Celtium | 4.35 ms | 2.27 ms |
| Celeritas | 1.41 ms | 1.56 ms |

Celtium is CPU-bound and loses half its clock when the package throttles; Celeritas is GPU-
bound and barely moves. The cool-state ratio is 1.45x, not 3.08x. Every ratio in this
project has to be taken with both arms at the same thermal state, and this release note
replaces the earlier number.
