# Celtium 0.1.4-alpha-rc.7 — post-chain resize retirement

Same build as rc.6 plus one use-after-free fix on the path a window or display resize takes
when a post-processing chain is running.

## The fix

`VulkanPostChain.target(identity, width, height)` replaces a chain target whose size changed
and destroyed the old image, its view and its framebuffer **in place**. A command buffer the
chain had already recorded can still name them, so the GPU could read freed memory - the
failure mode that RADV reports as `GPUVM fault`, then `CELTIUM_VULKAN_DEVICE_LOST`, then a
black screen because a lost device has nothing to present. The replacement is now retired
through `VulkanRetireQueue`, which drains only after a wait that actually succeeded. The
framebuffer cache's own resize/teardown paths were audited in the same pass and already
retire (or wait for device idle) before destroying.

This is a candidate for the tester's black screen, not a confirmed fix: that session's fault
does not reproduce here (same JAR, instance and mod set at 854x480 and 1920x1080, under
Xwayland and native Wayland, clean under the Khronos validation layer).

## Also in this build (unchanged from rc.6)

- Legacy immediate routes stay off (bisect); `-Dceltium.gless.legacyImmediate=true` re-enables.
- Crash breadcrumbs stay opt-in: `-Dceltium.vulkan.crashBreadcrumbs=true` keeps the last 96
  renderer operations and prints them only when the device is lost.
- 854x480 menu leg on this build: no device loss, no validation messages, every frame presented.
  World leg: P50 2.84 ms, no device loss, no validation messages.
