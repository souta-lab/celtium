# Celtium 0.1.4-alpha-rc.12 — two client-thread costs off the frame

Two measured costs removed since rc.11, both found by profiling the coalesced build.

## The entity membership epoch no longer spins

`EntityMembershipEpoch.current` was 3.0% of client-thread CPU on a Susy world profile. Both of
its methods were `synchronized` on the class and `current()` boxed its default value through
`getOrDefault`: the render thread was spinning on a monitor the entity tracker's `changed()`
holds, to read one long that almost never changes. The common case is now a volatile compare
against the world of the last ask, with the map read under the lock only on a miss.

## The per-group bind clocks are instrumentation again

`VulkanImmediateTexturePipeline.draw` called `System.nanoTime()` five times per group
unconditionally, and `clock_gettime` was 1.2% of client-thread CPU at about seventy groups a
frame. The counters it fed are measurement, not state the renderer reads, so they now sit behind
`-Dceltium.vulkan.bindTimings`.

## What the profile says now

After rc.11's coalescing, the raw-write path (which was 8-11% of client-thread CPU) is 0.4%,
and a world frame records one window: `windows=1 windowMain=48us` in the GPU pass line. The
frame is CPU-bound at a cool machine too (94.3% of wall in the render thread by `/proc`), with
the GPU waiting on it (terrain 375 us, immediate windows 48 us).

Susy world legs after these changes: warm P50 2.51-2.56 ms against 2.66 for the rc.11 pair;
that is within run-to-run noise, so no acceptance claim is made from it. The canonical plain
gate (guiScale=3 options, floors enforced, presented image judged) is PASSED on rc.11 and the
gates are re-run for this release.

## Still open

The FPS goal: at a cool machine state and the same conditions the paired ratios are about 1.5x
(Susy) and 1.45x (ATM3). The remaining cost is per-batch work and driver calls, not windows.
