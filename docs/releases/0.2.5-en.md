# Celtium 0.2.5

The stable release collecting everything since 0.2.4. The main points: terrain draws in the shadow pass now land in the shadow target for Demonica (an Iris-style shader-pipeline mod); the crash fix for creating a new world (#423) and the device-loss hardening ship in a stable release; and swapchain-image initialization was reworked into a form that is clean under Vulkan validation. Also included: multi-render-target (MRT) support, dynamic lights, and terrain performance work.

## Shadow-pass terrain draws now land in the shadow target

- This closes the limit rc2 stated — the shadow pass's terrain draws still landed in the frame target. A terrain pass now draws into the depth-sharing chain pair of the bound target (item 332), and the shadow gate is wired to a live signal that reflects whether a shader pack is in use (item 419). Candidates that point at the main depth are refused as main-depth.
- Measured on the validation fixture (AMD Radeon RX 6400, Demonica 0.9.1 + Complementary Reimagined r5.9.3, a local build with the guard removed): after the pack loads, the shadow pass activates and terrain draws into the 2048×2048 shadow target (ROUTED / DRAW) were observed. In the same leg, the presented frame passed its health check (presented verdict PASSED, no single-colour collapse).
- Shadow loading itself has run on the native path since rc2 (native depth copies served 8 or more times, refused 0).

## Fixed

- **Crash on creating a new world (#423, NVIDIA)**: the fix from rc2 ships in this stable release. On the path where another mod creates a framebuffer in the middle of a frame, Celtium's framebuffer cache could hand back an entry built for a frame target that no longer existed. Each cache entry now records what it was built over — the colour and depth views and the extent — and an entry that no longer matches is retired and rebuilt. If a frame target cannot be recreated to completion, the old target keeps being used, and at world teardown, cache entries keyed by the render passes that were just destroyed are always cleared. Stated plainly, as in rc2: the fix is verified by a code audit, unit tests, and the CI test suite, but the reporting environment — a GTX 1650 Ti with a large modpack — is not available locally, so the reporter's real-hardware check remains the deciding test.
- **Swapchain-image initialization reworked (item 515)**: the creation-time bulk initialization that rc1 introduced was itself a spec violation — it transitioned images that had not been acquired yet (7 Vulkan validation errors). Initialization now happens inside the present path, after the image is acquired, and the validation legs (AMD Radeon RX 6400 / Intel UHD 630) report zero validation messages. This initialization path is the one #422's purple tiles (RX 7900 XTX, on joining a world) were attributed to. The reporter told us on 2026-11-20 that the rc2 form did not resolve it on his machine; this release changes the initialization path itself, but **we do not claim #422 is fixed** — the retest on the reporter's real hardware is the deciding check.
- **Hardened against device loss (#425 family, item 416)**: if the GPU device is already lost during renderer reload teardown and similar paths, the client now records the failure and fails closed instead of crashing outright. Crash breadcrumbs were also expanded and exempted from the log limiter (item 415).
- **Translucent sorting hang (#424, item 424)**: quads with non-finite coordinates could make translucent sorting never terminate.
- More: fog attribute restore on attrib pop (item 420); the sprite pixel loop now carries booleans instead of the transparency enum (item 425); the lattice no longer throws on tall worlds and shadow search roots are remapped on window moves (items 493, 491); the trailing NUL Iris appends to shader sources is tolerated (item 371); fixed-function program attributes are read from the batch (item 374); batch-cache staleness fixes and retiring a stale batch before rebuilding it (items 391, 398).

## Performance

- Draw-list retention (D25): terrain batch assembly is retained across frames; on the validation fixture the terrain batch time went from 0.312 to 0.228 ms/frame standing still, and from 0.497 to 0.213 ms/frame while moving (measurements reported in rc2).
- Compact vertices (D23): the default vertex format is 24 bytes, reducing vertex memory by 25% per vertex.
- Geometry arena elements are aligned to whole primitives (item 421), and BoxFinder sorts its keys without boxing (item 489, with an equivalence test).
- The FPS KPI against Celeritas was again not re-measured (the real-pack measurement setup does not exist yet), and no performance superiority is claimed.

## Compatibility and other changes

- Multi-render-target (MRT): advertises `GL_MAX_DRAW_BUFFERS` / `GL_MAX_COLOR_ATTACHMENTS` = 8, lowers `gl_FragData` to per-location outputs, and supports draws into multi-colour chain pairs — the foundation for mod shader programs.
- Dynamic lights (D13): terrain shading reflects dynamic lights such as a held torch (since rc2; an A/B on the validation fixture confirmed the pixels around a light source brighten).
- Startup refusals: OptiFine, Vintagium and Relictium are refused at startup (item 311).
- The frame render pass is parameterised by colour format class (item 404); an idle/unfocused frame cap exists but is off by default (item 388); settled CPU texture data is released after load, with a census (item 387); the survival layer adds stage gates, post-chain self-quarantine, and safe-config migration (item 327).
- Release pipeline: SPIR-V re-validation from the shipped jar (item 353) plus the patch ledger and gate (item 356) — process changes, no behaviour change.

## Continuing limits

- A stock Demonica jar still will not enable shaders against Celtium, because Demonica's own QuarantineGuard pins the Celeritas jar's hash — as described in rc1.
- #422 and #423 both still await the reporters' real-hardware confirmation as the deciding test (above).
- Real-hardware rendering on Windows and macOS remains unverified, as in 0.2.4 (the CI test suite runs on all three OSes).
