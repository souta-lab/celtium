# Intel UHD 630: where the remaining gap to Celeritas is (2026-10-26)

Build `c89b007cf` (renderer sha256 `8e4304a2…`, async present on), Xaero instance, world scene, 1280×720,
KPI flags (validation off, readback off, `presentedDumpEvery=0`), warm ticks 400–600. Legs `fq-*`, `im-*`, `imd-*`,
`jf-*` (local, not kept). Celtium p50/p95/p99 2.32–2.37 / 3.72–3.80 / 4.49–4.65 ms; Celeritas 1.97–1.98 / 2.78–2.81 / 3.60–3.81 ms.

## Observations

- **GPU clock is not the difference.** `gt_act_freq_mhz` sampled every 50 ms: both renderers sit at 1050 MHz (max) in the warm window.
- **GPU frame (INTEL_MEASURE, renderpass and draw granularity):** ~2.2 ms in 13 render passes. The largest items are
  fancy clouds (2 × 15,984 indices, 320 + 280 µs; Celeritas pays the same, 2 × 10,656 vertices for ~578 µs), terrain
  solid (~430 µs), and the GUI's first fullscreen quad after its depth clear (vignette, ~227 µs; GL's fullscreen quads
  cost 140–190 µs). GL per-draw times overlap each other (their sum exceeds the frame), so GL totals are not comparable.
- **The game thread does not wait:** presenter joins ~0.35 µs per frame; the slot wait rounds to 0 ms per frame.
- **CPU (JFR, client thread, same 9 s window):** Celtium has 446 Java + 95 native samples; Celeritas has 265 Java +
  192 native. The game tick has the same share in both (3.6% vs 4.0%). We are cheaper on tile entities (112 vs 188
  inclusive) and more expensive in GUI + Xaero (148 vs 95) and in `flushImmediateWindow` (160, 25% of the thread).
- **`flushImmediateWindow` split:** queued draws 84, per-frame `beginCommands` 27 (`vkResetCommandBuffer` 14),
  per-window overhead ~40 (submit bookkeeping 13, acquire barriers 10, chain-pair clear 6, published-texture
  transitions 7). About 9.4 windows per frame (81,601 windows / 8,636 frames); Xaero's FBO binds alone are
  37 samples, versus ~0 on GL.

## Hypothesis and how to decide it

The gap is the window structure, not one hot spot. Every FBO bind ends a window, and each window pays its CPU
bookkeeping and a render-pass boundary on the GPU. One ordered stream with render-pass changes only at real target
changes (plan.md, next unit) should remove most of the ~40 samples and several of the 13 passes. The decision is a
paired KPI of that change on Intel: the window count per frame should drop, and `flushImmediateWindow` overhead
excluding draws should fall.
