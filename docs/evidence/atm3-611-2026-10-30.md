# ATM3 v6.1.1: Cleanroom Relauncher で起動・ワールド描画成功（2026-10-30）

## 経緯: v6.0.0-ptr3 から 6.1.1 へ

ptr3 は Cleanroom 0.7.14 で3つのブロッカーに当たった（実測）:

| # | 症状 | 原因 |
|---|---|---|
| 1 | `MissingModsException: wizardry requires librarianlib@[4.12,4.12]` | ptr3 の wizardry 0.9.6 が範囲固定。gist の LibrarianLib-Continuous 4.22 では満たせない |
| 2 | `VerifyError: Inconsistent stackmap frames` at `ModelLoader$VanillaModelWrapper.getTextures` | Fugue 0.25.5 が AE2 rv5 のモデルクラス変換で不正バイトコード |
| 3 | `IllegalArgumentException: Class versions V1_5 or less must use F_NEW frames` (EnderCoreTransformer) | EnderCore の ASM 変換が Cleanroom 0.7.14 の ASM と非互換（Fugue 無し時） |

gist は「**最新の ATM3**」を入れる手順なので、**v6.1.1**（GitHub `AllTheMods/ATM-3` master の manifest、261件）へ切り替えた。
6.1.1 では wizardry 0.11.1 が `librarianlib` を範囲指定なしで要求するため LL-Continuous 4.22 で満たせ、
AE2 も rv6-stable-7 になる。Fugue は 6.1.1 で VerifyError を起こさなかった（variant A: Fugue ありで起動成功）。

## 解釈

- **Celeritas は ATM3 でも動作する**（radeonsi で起動、paired の参照として有効）。
- 同一セクション数（12）・同一 tick での比較なので、差はレンダラ側。**Supersymmetry の 1.70 倍より大きい
  4.46 倍**で、KPI「Celeritas 超え」には大幅な性能改善が必要。
- Celtium の 10ms は小さなシーン（12 セクション）なので、地形描画そのものより**毎フレームの固定コスト**
  （即時window記録・flush・present・descriptor準備）が支配している可能性が高い。次に passSplit で内訳を取る。

| terrain / chunkUpload / setupTerrain | 0.2 / 0.1 / 0.2 | | |
| present（world 内） | 0.0 | 0.0 | 0.0 |

frame bracket は 2.9ms で、**warm P50 6.21ms との差 3.3ms は bracket 外**（ゲーム tick・present 呼び出し・
ループ）。一方 Celeritas の全フレームは 2.24ms なので、bracket 外に Celtium 固有のコストが残っている。

**run 間分散**: 同一条件（sections=12、ticks=1299、flags 同一）の Celtium アームで
warm P50 が **10.00ms（pair run）と 6.21ms（split run）** と 1.6 倍振れた。単発 run の比（4.46 倍）は
そのまま KPI に使えない。次回は各アーム 3 rep を取り、中央値で比較する（1 run 約10分、合計60分）。

## world-only 訂正（2026-10-30）

`keepGui=true` の warm 窓は GUI stage を含むため、world FPS としては過大だった。`keepGui=false` で測り直すと:

| arm | keepGui あり | **world-only** |
|---|---|---|
| Celtium | 9.75–10.00 ms | **3.42 ms** (P95 13.91, n=1914) |
| Celeritas | 2.24–2.26 ms | **1.25 ms** (P95 3.81, n=6401) |

両アーム sections=12・ticks=1299 で内容一致。**ATM3 の world-only 差は 2.74 倍**（以前の 4.4 倍は GUI 画面込み）。
残る課題は P95: Celtium 13.9ms vs Celeritas 3.8ms のスパイク。

## world-only paired の rep2 と分散（2026-10-30）

| arm | rep1 | rep2 | 備考 |
|---|---|---|---|
| Celtium | **3.42 ms** (P95 13.91, sec 12) | **5.25 ms** (P95 19.58, sec 11) | rep2 は `FAILED_PRESENTED_IMAGE`（画像verdictのみ。frame統計は有効） |
| Celeritas | **1.25 ms** (P95 3.81, sec 12) | **1.47 ms** (P95 4.83, sec 12) | 安定（1.18倍） |

- Celtium の rep 間分散は 1.5 倍（3.42 → 5.25）。rep2 は sections=11 で rep1 と内容が完全一致せず、
  また画像 verdict が FAILED（presented dump の窓判定）だった。frame 統計自体は 1299 ticks まで有効。
- Celeritas は安定。**中央値ベースでは Celtium 約4.3ms vs Celeritas 約1.36ms（約3.2倍）**。
- KPI 判定には rep を増やすか、sections と verdict を固定できる状態にしてから中央値を取る必要がある。
  「3.42 vs 1.25 = 2.74倍」は最良rep同士の比較であり、平均的な差はそれより大きい可能性がある。

## chunk upload budget の実験（既定OFF, 2026-10-30）

`sink`（後述）の spike を平準化するため、`celtium.vulkan.uploadBudget=N` を実装（既定 0=無効）。
完了した chunk 出力をその場で upload せずキューに積み、毎フレームの `setupTerrain` 先頭で N 件まで dran する。

| 条件 | warm P50 | warm P95 | capture |
|---|---|---|---|
| budget 0（既定, rep3） | 3.82 ms | 15.9 ms | sections 11、capture 成功 |
| **budget 8** | **3.37 ms** | **14.66 ms** | **capture 失敗**（`pinned-deadline listed 0 of 64, pendingP1=35`） |

- P50 は約12%改善するが、**起動時の chunk streaming が遅れ**、fixture の capture 条件（pinned sections）が
  成立しなくなった。`worldFrames=1385`, ticks=1299 で frame 統計自体は有効。
- 原因は起動直後の大量バーストに 8/フレームの上限が厳しすぎること。次段は「小さいキューは即時、閾値超えの
  バーストのみ上限」または「起動後 N フレームは無効」の適応型にする。
- 既定は 0（無効）のまま。実装と計器は残し、適応型の計測に使う。
