# Intel UHD 630: why p99 trails Celeritas (2026-10-28)

World scene, `world-0.7.11` instance (no Xaero), KPI flags, warm ticks 400–600, 1280×720, vsync off.

**p99はtickを含むフレーム（warm 200/5,700、3.5%）**: 通常フレームp99は同等（2.36–2.63 vs 2.46–2.52 ms）、tickフレームp95 3.88–4.08 vs 3.42–3.52 ms、
tick本体（ClientTickEvent）p50 1.27–1.32 vs 1.15–1.19・p95 1.55–1.80 vs 1.39–1.42 ms（`kpi4-intel`、計器 `frameIntervalWarmTickFrame*`/`warmTick*`、
`-Dceltium.debug.frameTail` の `CELTIUM_FRAME_TICK_SPLIT`）。tick差はvanillaコード全体に薄く分布（1 ms JFR: ChunkProviderClient走査+17/42サンプル等）。
棄却: animated sprite毎submitのtick単位batch化・stub sub-image変換のscratch化（control比1.002）、CPU/GPUクロック差（両arm 3800/1050 MHz）、JIT deopt反復（9件）、
フレーム数による干渉（120 fps上限で同フレーム数でもtick 1.22 vs 1.06 ms）。差はvanillaのメモリ参照（chunk map get・HashMap走査・getBlockState）に広く分布。
仮説: Vulkan記録がmain threadのキャッシュを奪う（Celeritasはmesa `gdrv0` 別コア）。判別にはperf（未導入）か記録の別thread化の上限測定。
tick後フレームの+0.3 msは `CELTIUM_FRAME_TICK_PASSES`: clouds区間（その時点の即時window flushのnative submit）+53 µs・setupTerrain +33 µs・flush +24–73 µs。

Also rejected: a larger code cache (`-XX:ReservedCodeCacheSize=512m`, tick p50 1.31 vs 1.33 ms) and disabling mesa
glthread on the reference (its tick did not slow: 1.06 vs 1.14 ms), which weakens the cache hypothesis.

After the glass, lit-clamp and block-pipeline fixes (`kpi5-intel`, p99 ratio 1.051): tick-frame p50 is level
(3.15–3.26 vs 3.11–3.22 ms) and the gap is the tick frames' upper tail (p95 3.83–3.90 vs 3.48–3.61 ms; tick p95
1.57–1.60 vs 1.35–1.41 ms). `warmTickSlowest` (fixture, warm window) shows four 4–7 ms ticks about 35 ticks apart
under Celtium and none over 1.6 ms under Celeritas; they carry no Java samples (a pause or native wait, not code),
and four frames cannot move a percentile of ~5,900, so the p99 is the broad tick tail. Texture uploads already share
the frame's batched submission, so per-upload queue submits are not it.

Window structure on the current build (`ws-intel`, `-Dceltium.vulkan.drawSiteCensus=true -Dceltium.vulkan.frameStats=true`):
seven windows a frame; three are opened by immediate flushes, each ~3,400 times over the run — before the terrain
layer (`RenderSectionManager.renderLayer`, the sky and anything drawn before terrain), at the world pass end
(entities, block entities, particles), and at the main framebuffer's unbind (hand and GUI) — and the rest are the
terrain passes' own render passes and submits. Window recording on the client thread: 0.35 ms a frame. Folding them
into one render pass and one submit needs the terrain passes and the immediate groups in one ordered command stream
(plan Stage 4), the same size of change as moving the recording to an executor thread.

## 2026-10-28 夜: 棄却した仮説（Intel、world-0.7.11、warm 400–600）

- **GC・client thread の CPU**: 割り当てを約6割減らした jar `4b822a94`（光量キャッシュ・計数停止を含む）は、同一run内対照
  （0.1.1-alpha）に対して p50 0.999倍・p99 3.52–3.85 vs 3.48–3.64 ms で変化なし（`k6-intel`、Celeritas比 0.901/0.867/1.068）。
- **safepoint**: `-Xlog:safepoint` で warm 窓の停止は young GC 2回（約3 ms）だけ。約6000フレーム中2–3フレームでは p99 は動かない。
- **非同期の遮蔽探索スレッド**: `-Dceltium.terrain.asyncOcclusion=none` と既定を交互に3回ずつ: p99 3.71/4.03/3.87 vs 3.60/3.61/3.56 ms。
  探索を止めても改善しない（悪化）。
- 残る仮説: 描画側のメモリ使用が L3 を追い出し、vanilla の tick（`WorldClient.tick` が大半）を遅くしている。判別には tick 区間の
  キャッシュミス計測（perf の LLC-load-misses）を両 arm で取る。
