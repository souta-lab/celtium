## The GUI scale had to be pinned

The first attempt was refused: `r130kpi-amd-celtium-r1` ended `fixtureStatus=UNCALIBRATED_PRESENTED_IMAGE` and the
KPI script rejected the leg. The report named the reason exactly:

```
floorsNotCalibrated = FLOORS NOT CALIBRATED for scene world ... this run is not the variant it describes
  (default flat stack, guiScale=2 (NOT the scale the panel floors were measured at: 3))
sceneCalibrationKey = ... guiScale=2
sceneReferenceCalibrationKey = ... guiScale=3
```

The `celtium-world-accept` instance's `options.txt` now carries `guiScale:2`; the reference floors were measured at
`guiScale=3` (auto at 1280x720). The KPI legs therefore pass `-Dceltium.validation.guiScale=3` as a shared flag, which
the fixture records as `guiScaleForced=3`, and the key matches (`sceneCalibrationKeyMatches=true`). This is a
reproducibility fix, not a renderer change: the same flag is passed to both arms.

## Where the p99 comes from: the tick frame's upper-middle

The fixture splits the warm window by frame kind. 200 of the ~4 200 frames are tick frames, so the 99th percentile of
all frames is the ~79th percentile of the tick frames - the p99 is a tick frame, and it is not the tail of the tick
distribution (the tick p95 is higher).

| GPU | arm | tick p50 | tick p95 | plain p95 | plain p99 | client tick p50 |
|---|---|---|---|---|---|---|
| AMD | Celtium | 4.966 / 4.794 / 5.079 | 6.216 / 5.775 / 7.729 | 2.954 / 2.679 / 2.800 | 3.557 / 3.314 / 3.302 | 1.698 / 1.703 / 1.791 |
| AMD | Celeritas | 4.947 / 5.117 / 4.886 | 5.932 / 6.260 / 5.730 | 3.162 / 3.012 / 2.996 | 4.312 / 3.895 / 3.832 | 1.694 / 1.698 / 1.641 |
| Intel | Celtium | 6.567 / 5.572 / 6.206 | 7.977 / 6.654 / 7.796 | 4.462 / 3.703 / 4.274 | 5.840 / 4.728 / 6.013 | 2.336 / 1.979 / 2.286 |
| Intel | Celeritas | 6.309 / 6.134 / 6.249 | 7.286 / 7.226 / 8.206 | 4.593 / 4.542 / 4.679 | 5.487 / 5.409 / 5.798 | 2.285 / 2.253 / 2.294 |

Three facts, all measured on the same legs:

1. **Plain frames are 10-15 % faster than Celeritas** (AMD p95 2.68-2.95 against 3.00-3.16; Intel 3.70-4.46 against
   4.54-4.68). The renderer's steady-state path is not the problem.
2. **The client tick is the same** (AMD 1.70 against 1.69; Intel 2.29 against 2.29 at the median). The simulation is
   not the problem.
3. **The tick frame's spread is wider**: Celtium's tick p95 minus tick p50 is 1.1 ms on AMD and 1.6 ms on Intel;
   Celeritas's is 1.0 ms and 1.0 ms. Celtium's tick p50 is equal or better, its tick p95 is worse, and the p99 lands
   between them.

So the remaining gap is the tick frame's upper-middle: the frames where the world changed and the renderer has more
immediate groups to record. The immediate path costs ~2.3 us a group (122 groups a frame on the diagnostic leg,
`grpDraw` ~1 us of it), and a tick frame carries more groups than a plain one; Celeritas's GL draw is a fraction of
that, so the same increase in group count costs Celtium more. That is the mechanism to attack next, and it is a
group-count / per-group-cost problem rather than a simulation or steady-state one.

Two tick spikes appear in the warm window of some runs and not others (Celtium 18.7 ms at tick 555 and 29.6 ms at tick
508; Celeritas 11.6 ms at tick 410). They are the top two frames of their runs, not the p99, and they appear in both
arms - they are machine noise (GC or scheduling), not a renderer property.

## Reproduce

```sh
CELTIUM_KPI_GPU=amd CELTIUM_KPI_JARS=.gv-verify/jars/r130-kpi \
CELTIUM_KPI_REFERENCE=.gv-verify/lib/01-celeritas-forge-mc12.2-2.5.0-dev.jar \
CELTIUM_KPI_REPS=3 scripts/gv-kpi.sh r130kpi-amd 240 -Dceltium.validation.guiScale=3
```

The result JSONs are `.gv-verify/r130kpi-{amd,intel}-kpi-result.json`; the per-leg reports are under
`.gv-verify/run-r130kpi-{amd,intel}-{celtium,celeritas}-r{1,2,3}/logs/celtium-validation.json`.
