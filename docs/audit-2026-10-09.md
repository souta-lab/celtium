# External audit, 2026-10-09 - findings and status

Fixed HEAD audited: `f3ac1844b`. Findings are reproduced here with what was done about each, so the plan itself stays
short.

## A - P0, confirmed and fixed: `VkSubmitInfo.waitSemaphoreCount` was zero

Verified from the LWJGL 3.4.1 bytecode: `VkSubmitInfo.npWaitSemaphores` writes only the pointer, so a `calloc`'d struct
waits on nothing. Both submission sites now set the count explicitly (`VulkanTerrainGpuBackend.submitCommands`,
`VulkanContext.submitWithSemaphores`); `VkPresentInfoKHR` needed no change because its setter does set the count, which was
also verified rather than assumed.

Measured after the fix: frame present **PASSED, `nativeTerrainVerified True`, 2148 passes, zero validation messages** (36
before). The log's earlier "the layer's view of external semaphores" hypothesis is retracted in the history file.

## Verified after the A fix, with synchronization validation on

| AMD default (terrain + immediate, no present) | PASSED, `nativeTerrainVerified True`, 1673 passes, **0 messages** |
| Intel, frame present enabled | PASSED, `nativeTerrainVerified True`, 884 passes, **0 messages** |
| AMD, frame present enabled (measured earlier in the round) | PASSED, `nativeTerrainVerified True`, 2148 passes, **0 messages** |

Both drivers, with `VK_LAYER_ENABLES=...SYNCHRONIZATION_VALIDATION_EXT` set as the run scripts do.

## F - P1, confirmed and fixed: the harness accepted validation errors as success

`scripts/prism_validation.py` now reads the whole log after the process exits and fails the run if the layer reported any
message, with `validationMessageCount`, `validationClean` and `validationFirstMessages` in the result so the two things the
audit asked to keep apart stay apart. The detection was checked against logs with known contents: the pre-fix probe log
yields 2 messages (so that run would now fail) and the post-fix default log yields 0.

This is the guard whose absence let a PASSED run contain thirty-six messages: the fixture's counters only see the
renderer's own errors, and the layer reports into the log.

## F follow-up - the reported codes now carry the verdict

`validationExitCode` becomes 1 when the layer reported anything, and `fixturePassed` and `validationClean` are separate
fields, so a PASSED fixture with messages is a failed run rather than a passing one with a footnote. That is what the C
measurement above used to fail before the fix and pass after it.

## Open from the audit

- **B (P0)** - *core fixed and verified.* The contract was explicit in `VulkanFrameTarget`'s own documentation: the
  caller's submission must wait `waitSemaphore()` and signal `doneSemaphore()`, "waiting for a submission that was never
  sent deadlocks the render thread". `VulkanContext.submitWithSemaphores` now takes several wait and signal semaphores with
  explicit counts, and `presentImage` uses one submission to satisfy both contracts at once - it waits the window-system
  acquire **and** the bridge semaphore, and signals its own render-finished semaphore **and** the bridge's. Measured after
  the change: **PASSED, `nativeTerrainVerified True`, 2152 passes, `validationMessageCount 0`, `validationClean True`**.
  The caller no longer treats a failure as success either: `presentImage` records whether its submission was made and
  whether the frame reached the screen, and the caller ends the frame only when the submission happened and leaves GL's
  composite in place when the present did not. Measured: **PASSED, `nativeTerrainVerified True`, 2159 passes, 0 messages**,
  with `submitDone=true succeeded=true` reported on the first present. Getting there needed one measurement rather than a
  guess: the first attempt broke the run because the flags were set in the probe instead of `presentImage`, so `submitDone`
  read false and skipping `endFrame` dropped the bridge's copy-back.
  **The layout half is done too.** `VulkanFrameTarget` tracks the layout of its own shared colour image - its commands are
  the only ones that move it, since GL's blits are not Vulkan commands - and the present path reads that instead of being
  told a layout, then hands the image back with a barrier from `TRANSFER_SRC_OPTIMAL` to the layout the target expects.
  Verified: **present path PASSED, 3264 passes, 0 messages; default configuration PASSED, 1665 passes, 0 messages**, both
  `validationClean True`.
  **Recreation now exists.** `VK_SUBOPTIMAL_KHR` and `VK_ERROR_OUT_OF_DATE_KHR` from both the acquire and the present are
  recorded instead of being accepted silently, and the backend drops the swapchain when it sees that, so the next present's
  `ensureSwapchain()` builds one against the surface as it is then - the lazy creation that already existed is the whole
  rebuild. Verified that the healthy paths are unaffected and the rebuild stays dormant unless a driver asks for it:
  **present path PASSED, 3256 passes, 0 messages; default PASSED, 1652 passes, 0 messages; the out-of-date branch not taken
  in either.** The branch itself is not exercised - this harness cannot drive a resize and neither driver reports
  sub-optimal at this size - so it is built and compiled, not demonstrated.
- **C (P1)** - **fixed and verified.** The reported VUIDs were reproduced first: the reload run measured
  `validationMessageCount 13`, `validationClean False`, led by "vkDestroyBuffer(): can't be called on VkBuffer ... that is
  currently in use by VkCommandBuffer" - so the audit's finding was real, and the new harness guard reported it.
  `settleGpu(reason)` now ends the device's work before anything is released, at `delete()` and at region eviction, with a
  message rather than a hang if the device stops making progress. Measured after the change, all with the harness guard
  active: **reload on the RX 6400 and on the UHD 630, and the world-leave/rejoin path, all report
  `validationMessageCount 0`, `validationClean True`, fixture PASSED, `nativeTerrainVerified True`** (897, 585 and 885
  passes respectively). With waits now real, releasing before the GPU finished would have become worse over time, which is
  why this moved ahead of the remaining P0.
- **D (P1)** - **re-evaluated and addressed.** The one-window limit existed because a second window in the same frame had
  measured as a black frame - and that measurement predates the submit-wait fix, so the black frame had a sufficient
  explanation in handoffs that were never waited on. Re-measured after the fix: **sixteen windows per frame is
  pixel-identical to GL** (0.00 mean, 0.0% of pixels over 8). The cost was checked before raising the limit - frame interval
  p50 16.07ms and p99 17.90ms at sixteen against 16.13ms and 18.16ms at one - so the default is sixteen, which draws each
  batch in the frame that produced it and makes the plan's "lag-free" statement true rather than contradicted. Verified with
  no flags on both GPUs: **AMD PASSED, 1645 passes, p50 16.08ms, 0.00 difference; Intel PASSED, 1103 passes, p50 23.93ms,
  0.00 difference**. The deferral counter stays as the evidence if the limit is ever reached, and the deeper design point
  the audit raises - that acceptance must be guaranteed before GL's draw is cancelled - is recorded as still open for
  batches that exceed it.
- **E (P1)** - **fixed, with one acceptance the audit asks for still outstanding.** `waitForIdle` is submission-aware and
  bounded: it returns without waiting when nothing was submitted, clears its pending flag only once the wait resolves,
  reports a timeout instead of hanging, and drains the queue only after the fence actually signalled. The frame paths are
  fail-closed too: whether this frame's submission reached the queue is recorded **per frame** by the submission itself and
  read immediately before `endFrame`, so a frame whose submission and recovery both fail is left unended with a loud record
  instead of waiting GL on a semaphore that was never signalled.
  The first attempt used the backend's `submissionPending` for that test and refused to end every healthy frame - the run
  fell to a single terrain pass, because that flag is cleared by the idle wait before `endFrame` runs. Measured with the
  frame-level flag, default configuration, no flags set: **AMD PASSED, 1668 passes; Intel PASSED, 1089 passes; both
  `validationClean True`**; with the present enabled, 3216 passes and clean.
  **The acceptance is now met.** `-Dceltium.vulkan.failSubmits=N` refuses the first N submissions, so the path can be
  exercised rather than only compiled. With two refusals (the frame's submission and its recovery) the run reports:

```
injected submit failure (1 left): this submission is not sent
no submission reached the queue this frame, so the frame is not ended and GL is not left waiting on a semaphore that was
never signalled
fixture FAILED | passes 1 | errors=1647
harness: exited in 26s
```

  The fixture failing is the intended outcome of an injected fault; what matters is the **bounded time**. 1647 frames each
  found no submission, and the bounded wait they avoided is five seconds - so a run that waited instead of failing closed
  would have taken hours, and this one ended in twenty-six seconds. The external watchdog is the harness's own process
  timeout, which did not need to fire.
- **G (P2)** - **fixed.** The two `glReadPixels` samples and the state snapshot around each mid-frame window were outside
  the sample-count guard, so they ran on every window of every frame in the shipped configuration. They are now behind
  `-Dceltium.vulkan.immediateWindowSamples`, off by default. Verified: default run **PASSED, `nativeTerrainVerified True`,
  1679 passes, `validationClean True`**, and the diagnostic line no longer appears in the log. The frame time did not move
  measurably (p50 16.08ms before against 16.11ms after, p99 18.39ms against 17.60ms), so the honest claim is that the
  synchronous stalls are gone from the default path, not that the game got faster.
- **H (P2)** - **fixed and verified.** The query-pool creation, `TerrainGpuBackends.install(this)` and the swapchain probe
  all sat inside one `if (timestampsUsable)` block, so a device whose queue cannot record timestamps lost the backend
  entirely - a direct contradiction of choosing features by capability. Registration and the property-gated probe are now
  outside it, and only the query pool is conditional, with a message saying pass timing is off. Verified by forcing that
  path on hardware that does support timestamps (`-Dceltium.vulkan.forceNoTimestamps=true`): **PASSED,
  `nativeTerrainVerified True`, 1658 passes, `validationClean True`**, with the log line "the queue cannot record
  timestamps, so pass timing is disabled; the backend registers anyway". The forced switch is not a real device without
  timestamps, and the audit file says so - what it demonstrates is the branch's behaviour, which is the part that was
  wrong.

## Additional lifetime and WSI notes

- **Render-finished semaphores are keyed to the image, not to a cursor - fixed and verified.** A cursor can hand out a
  semaphore whose previous presentation has not retired; the image index cannot, because the presentation engine only
  returns an image once its previous presentation is done. That is the guarantee the reuse needs, and it is now what the
  code uses. Verified on both present paths with the harness guard active: **frame present PASSED, 3252 passes, 0 messages;
  the clear-and-present probe PASSED, 1675 passes, 0 messages.**
- **The `FRESH_SEMAPHORES` pairs are tracked and destroyed with the swapchain - fixed.** The experiment created a pair per
  present and never freed them, which leaks a semaphore per frame; they are now held in a list and destroyed after the
  queue drains. The path is off by default and stays that way; what mattered was not leaving a leak behind a switch
  somebody might turn on.
- **Still open from this group:** swapchain recreation on `VK_ERROR_OUT_OF_DATE_KHR` or a resize, which the project has no
  path for yet (and cannot exercise, since this harness cannot drive a resize - recorded under B and in the plan), and
  verifying the framebuffer/texture mirrors against target-dimension changes, GL name reuse and deletion.

## Resize: the harness could exercise it after all

The audit's notes and this project's plan both recorded resize as unverifiable here, because the fixture's
`glfwSetWindowSize` was accepted by the window and Minecraft's framebuffer never changed. The right entry point was
Minecraft's own `resize(int, int)` - public, and it sets `displayWidth`/`displayHeight`, recreates the game framebuffer,
resizes the shader group and notifies the current screen - which does not depend on the window manager at all. Driving that
mid-run takes the frame from 1280x720 to 1024x640 and measures:

```
fixture PASSED | nativeTerrainVerified True | 1652 passes | messages 0 | clean True
capture 1024x640
```

It also **found a real defect**, which is the point of being able to drive it: the first run with the resize reported

```
vkDestroyFramebuffer(): can't be called on VkFramebuffer ... that is currently in use by VkCommandBuffer ...
```

- the frame target being released on the resize path without waiting for the GPU, the same class as C but on a path C's fix
did not cover. `settleGpu("frame target recreation")` now runs before it, and the run is clean.

## Second audit round

### A (P1, blocking every migration claim) - the injector was never cancellable

Confirmed from the code as reported: `WorldVertexBufferUploaderMixin`'s injector was declared
`@Inject(method = "func_181679_a", at = @At("HEAD"), require = 0)` with **no `cancellable = true`**, and its
`info.cancel()` sat inside `catch (Throwable ignored)`. `CallbackInfo.cancel()` on a non-cancellable callback throws,
that throw was swallowed, and **the original GL draw ran for every batch the backend had accepted** - so Vulkan and GL drew
the same geometry, the images agreed, and no comparison in this project could tell the difference. Every count of
"accepted" batches was a count of intent.

**Fixed:** the injector is now `cancellable = true`; the acceptance is recorded in a flag, the broad catch returns early
without swallowing the cancellation, and when a batch is accepted the mixin now calls `buffer.reset()` and then
`info.cancel()` - matching what the vanilla method does after its upload, which cancelling would otherwise skip.

**Measured, and the result is that replacement is not happening.** The audit's instrument was built: a second injector on
the same method at `RETURN`, counting how often the vanilla upload body completes, printed beside the offer count. The run
reports:

```
celtium uploads: offers=10000 glUploads=10028
```

The injectors do run - ten thousand offers - and **the GL upload body completes about as often as it is offered**. So
whatever the backend decides, GL is uploading for essentially every batch: the migration effect this project has been
describing is **not** in place, and the frames that measured 0.00 agreed because GL drew them.

**Resolved, and the cause was two defects stacked.** Counting the decision inside the mixin - the channel that reaches the
log - printed `offers=10000 accepted=0 glBodyCompleted=10029`, and the swallowed-failure report never fired, so no exception
was hiding it: the backend was simply never asked. Checking the call site showed why - **the `submitImmediateBatch` call
had been deleted from the mixin** when a dead branch was cleaned out of that method in the previous round, and with it went
the only path by which a batch could ever be accepted. That is why the backend's counters read zero and GL drew everything.

With the call restored, the audit's criterion is met:

```
celtium offer decisions: offers=10000 accepted=562 glBodyCompleted=9465
backend counters: immediateOffered=8935 immediateTaken=577 immediateFlushes=57
fixture PASSED | nativeTerrainVerified True | 2208 passes
```

**Replacement now demonstrably happens**: the backend is called, it accepts 562 batches, and the vanilla upload body
completes 535 fewer times than it is offered - GL is skipped for exactly the batches Vulkan takes. The remaining refusals
are the acceptance mask and the format rules doing their jobs, and the counters agree with the mixin instead of
contradicting it.

So the sequence that produced this project's false account is now on the record in order: the missing `cancellable` made
cancellation ineffective, the deleted call made acceptance impossible, and each defect alone was enough to leave GL drawing
every frame while the counters and the images said nothing was wrong. **The comparisons now have to be run again from the
start**, which is what the audit asked for and what the next round does.

### B (P0, on the `presentFromComposite` path only)

Confirmed: `VulkanSwapchain.presentImage`'s seven-argument form receives `bridgeWaitSemaphore` and `bridgeDoneSemaphore`
and **never uses them**; the submission still waits only the WSI acquire and signals only its own semaphore, while the
backend's `endFrame` makes GL wait on the bridge's done semaphore. The docs' earlier "B fixed" is **wrong** and is
corrected here: the waits must be `[acquire, bridgeWait]` and the signals `[renderFinished, bridgeDone]`, together with the
shared image's ownership and layout handoff, and the success flags reset at the start of every present. The path is off by
default, which is why this has not been visible.

### C (P1, the comparator)

Confirmed: `compare_validation.py`'s difference mask converts the RGBA difference to luminance rather than taking the
maximum per channel, so a red-only difference of 1 with tolerance 0, a blue difference of 40 with tolerance 5 and an alpha
difference of 255 with tolerance 0 all read as **equal with zero differing pixels**. The fix is `max(abs(channel)) > tol`,
and the results computed with it need recalculating. The comparisons quoted in this project's history were measured with
inline maximum-per-channel arithmetic rather than that function, so they are not affected - but the tool is wrong and is
being fixed.

## The first measurement of the Vulkan path drawing alone

With the call restored, the water scene was re-measured against same-revision references - the first comparison in this
project where the immediate path genuinely replaced GL:

```
floor (reference against reference):       mean 0.00 | 0.00% of pixels over 8
water scene, Vulkan drawing alone:         mean 0.00 | 9 pixels of 921,600 over 8
counters: immediateOffered=9060 immediateTaken=585 immediateFlushes=585
fixture PASSED | nativeTerrainVerified True | 2211 passes
```

585 batches were drawn by Vulkan and skipped in GL, and the frame matches the GL reference to **nine pixels** out of
921,600. That is the first evidence this project has that the immediate path renders correctly at all - every earlier
comparison had GL drawing the same content - and it is stated as nine pixels rather than as "identical", because nine
pixels is what the measurement says.

Where those nine pixels are is the next question, and it is now a question worth asking: 226..227 by 504..506 is a small,
localised spot rather than an edge or a band.

### After replacement: the particle scene differs, cause not identified

Re-measured with the immediate path actually replacing GL, the weather and particle scene differs from its same-revision
reference by **1.32% of pixels over 8 (12,157)** against a **0.23%** floor - about five times the floor, so larger than the
scene's own variation, and the floor is non-zero because particles animate in time. An earlier reading of the same run
claimed the counters showed accepted geometry going undrawn (`taken=586`, `flushes=58`); that was a **truncated**
`immediateFlushes=586`, and the claim is withdrawn. Both scenes take and flush in equal numbers, so no mechanism is
attached to this difference yet.
