## #2a の訂正（2026-10-15・vanilla ソースで確定）

**「blur がかからない」は Celtium の欠陥ではない。vanilla 1.12.2 には blur が無い。**

vanilla の `GuiScreen.func_146270_b`（= `drawWorldBackground`）は、world があるとき
`drawGradientRect(0, 0, width, height, 0xC0101010, 0xD0101010)` を引くだけで、**ぼかしは一切しない**。
world が無いときは `options_background.png` を 32px でタイルし `0x404040` で塗る。
利用者のスクリーンショットの暗いグラデーションは**この仕様どおり**である。

ぼかしは **`tterrag1098/Blur` という別 Mod の機能**で、利用者の 16 mod 構成には入っていない。
したがって **#2a は「入っていない Mod の機能を期待している」**であり、修正対象ではない。
**記録から欠陥として数えない。**

一方 **#2b（ビデオ設定で暗幕すら無い）は実バグ**として残す。

## #5 の見立て（利用者の要求どおり、原理的に可能かを明示する）

**原理的に不可能ではない。** ただし経路が2つあり、どちらなのかを先に確定させる必要がある。

- Cleanroom の起動ロゴは `SplashProgress` 系（Forge 由来）で、**GL で描く**。GL-less 経路には GL context が無いので、そのままでは描けない。**これは「描けない」ではなく「native pass がまだ無い」**。
- 一方で「**表示されない**」という観測は、**描画が失敗している**のか **そもそも呼ばれていない**のかを区別していない。Cleanroom は `SplashProgress.finish()` を早期に呼ぶ経路があり、それが走っていれば**描く機会自体が無い**。

したがって次の順で確定させる:
1. ログに `CELTIUM_SPLASH_HOOK` が出ているか（既存の計器。出ていれば hook は呼ばれている）
2. `SplashProgress` の描画が native pass を持っているか
3. 上記2つで「呼ばれていない」なら**原理ではなく起動順序の問題**であり、修正可能

**「不可能」と断定するのは、1〜3 を測ってからにする。** 現時点で断定しない。

## 追加報告（2026-10-15・利用者）— **回帰である**

利用者が3件を追加報告し、**「これもともとできてたのにできなくなってる」**と明言した。**回帰**である。

| # | 報告 | 意味 |
|---|---|---|
| **6** | **エンティティが見えない** | entity pass の描画が消えた |
| **7** | **プレイヤーも見えない** | 同上（player は entity 経路） |
| **8** | **雲も見えない** | cloud pass の描画が消えた |

**3つが同時に消えたことは共通根因を意味する。** terrain は出ている（利用者のスクリーンショットで地面とブロックは見える）ので、
**「terrain 以外の pass が一様に描かれていない」**という形である。

**最有力の仮説: 描画が「拒否」されている。** AGENTS.md が明記しているとおり、
**GL-less の窓では拒否された batch は誰も描かない**（拒否は fallback ではない）。
計画には `CELTIUM_REFUSED` 系の計器と「描画拒否がゼロ・`presented` 565」という実測記録があり、
**`lm8`（jar `25b6da53…`）の時点ではゼロだった** — つまり**その jar と 0.0.5 の間で回帰した**。

**したがって二分探索が可能**: `lm8` の jar（`25b6da53…`）と 0.0.5 の jar の間で counter を比べれば回帰点を挟み込める。

**Mesa の仮説は棄却された（利用者の訂正・2026-10-15）**

MC-296889/MC-300939 の一族（entity/player/item が見えない）は Mesa 25.0.0-dev のドライババグで
25.1.x で直る、と Mojang に Invalid とされている。**しかしこれは我々の case ではない**:
利用者が「**同じ Mesa でできていた**」と訂正した。実測も一致する — このマシンは
`/usr/lib/x86_64-linux-gnu/libvulkan_radeon.so` = **Mesa 26.2.4-1**（Debian, 2026-10-02）で、
leg の記録も全 leg で `apiVersion 1.4.354` の同一ドライバである。

**したがって回帰は Celtium のコード側にある。** 外部の類似事例に引っ張られて原因を外へ帰すのは、
失敗するゲートを「計器の会計」と言い換えるのと同じ誤りである。

**候補は3つ**（この単位で main に入った変更）:
- **#285** 間接コマンドバッファのページング — terrain 経路（entity/cloud は別経路）
- **#286** framebuffer 破棄前の `settleGpu` — **`vkDeviceWaitIdle` を破棄経路へ足した**ので描画パスを止めうる
- **#287** `require = 0` — 注入の有無を変えないので**原因ではない**と考えられる

**決定的な実験**: 旧 jar `25b6da53…`（`gv-cohort-lm8`。**「描画拒否がゼロ・presented 565」を記録した jar**）と
現行 jar を**同じ scene** で走らせ、**entity/cloud の counter を比べる**。これが回帰点を挟み込む。

**参考（外部の裏づけとして残す）**:
MC-300939「**the entities seem not be rendered at all. The world is overall working and rendered correctly, but
the inventory, the avatar, animations, and some object (such as beds, boats, and animals) aren't visible**」は
**AMD Radeon 機の Linux で、1.21.6 から出た回帰**として報告され、MC-296889 の重複として追跡されている。
「**1.21.5 では完璧に動く**」とも書かれている。**我々の症状（地形は出る・entity/player/cloud が出ない・Radeon・回帰）と同型。**

**読むべき計器は既にある**（新規に作らない）:
- `CELTIUM_MODEL_QUAD_REFUSALS` / `CELTIUM_MODEL_QUAD_REFUSED` — **entity/model 経路**（利用者の #6/#7 に対応）
- `CELTIUM_ZERO_VIEW_REFUSAL` — immediate item/texture 経路（#1 のアイテムにも関係しうる）
- `CELTIUM_MIRROR_PATCH_REFUSED` / `CELTIUM_COMPOSITE_LAYOUT_REFUSED` / `CELTIUM_POST_*_REFUSED`
- `CELTIUM_DRAWN_SECTIONS` / `CELTIUM_DRAW_SITE` — terrain（**こちらは出ている**）

**計画の記録では round 691 の時点で「VUID 0・拒否 0・458,000 バッチ描画」**である。**その時点の拒否はゼロ**なので、
**回帰はそれ以降の変更にある。** 次の実測は「現在の jar でこれらの counter を読むこと」であり、推測ではない。

**#287 は原因ではない**と考えられる: `require = 0` は「対象が無いときに致命的にしない」だけで、
注入の有無も描画の有無も変えない。回帰は **#285（地形の間接ページング）か #286（framebuffer の settle）**、
あるいはその間の別の変更にある可能性が高い。**ただし決めつけず、まず計器を読む。**

## 共通根因（2026-10-15 に特定）

**#2・#3・#4 は「GUI の下に世界／パノラマが描かれていない」という同一根因である。**

1.12.2 の `GuiScreen.drawWorldBackground(int tint)` は、**world があれば世界の上に暗幕を引き、無ければ dirt 背景を敷く**。
利用者の報告は #2・#3・#4 のいずれも「背景が一様な暗色／単色」で、**世界もパノラマも透けていない** — これは
「暗幕だけが描かれ、その下の世界が描かれていない」形と一致する。#3 のベージュ一色も同じ説明がつく
（Advancement 画面の背景は本来 dirt か世界で、単色ベタではない）。

**パノラマの経路は既に計器を持っている**（だから「無い」ではなく「描けていない」を測れる）:
- `TextureCopyService.java:121` — `GuiMainMenu.renderSkybox -> drawPanorama -> ro...`
- `TextureCopyService.java:320` — 「Which caller issues the copy: the panorama's is `GuiMainMenu...`」
- `TextureCopyService.java:537` — 「`renderSkybox`'s final composite quad likewise: at 38%」
- `VulkanTerrainGpuBackend.java:12457` — 「The main menu's panorama is the measured caller」
- `GllessFrameTarget.java:1011` — 「the main menu's panorama work: `GuiMainMenu.renderSkybox`」

**受入は `CELTIUM_TEX_COPY_SERVED ... mean=` 行**（fixture の `menuHoldTicks` のコメントがそう定めている）。
つまり **#4 は「計器が出ているのに絵が出ていない」なのか「計器も出ていない」なのかで分岐する** — 次にそれを測る。

**#1 は独立**で、アイテム/ブロック entity のテクスチャに filter か mipmap が掛かっている疑い
（地形の atlas とは別経路）。
