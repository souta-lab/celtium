## 実測で確定した2件（2026-10-15・leg `gv-cohort-menu1`・AMD・jar `0ded6648…`）

### #6/#7 の根因 — モデル quad が `unknown-list` で拒否されている

leg のログに**拒否の実物と call site**が出た:

```
CELTIUM_MODEL_QUAD_REFUSED reason=unknown-list list=0 read=GL_TEXTURE_BINDING_2D unit=33984 texture=0 vertices=4
  callSite = net.minecraft.client.model.TexturedQuad.handler$zee000$celeritas$celtium$captureQuad
          <- net.minecraft.client.model.TexturedQuad.func_178765_a
          <- net.minecraft.client.model.ModelBox.func_178780_a
          <- net.minecraft.client.model.ModelRenderer.func_78788_d
  (captured=0 refusedUnknownList=1 refusedUnknownTexture=0 refusedDegenerate=0)
```

**機構が全部つながった**（原典で確認）:

```
ModelRenderer.render(scale)
  if (!compiled) compileDisplayList(scale)
      displayList = GL11.glGenLists(1)                    // GL の display list
      GL11.glNewList(displayList, …)
      for (ModelBox box : cubeList) box.render(BufferBuilder, scale)
          for (TexturedQuad quad : quadList) quad.draw(Tessellator, scale)   // 我々の captureQuad
      GL11.glEndList()
      compiled = true
```

`glGenLists` / `glNewList` / `glEndList` は **GL の display list API** で、GL-less では stub される。
だから `compiled` が真にならず `displayList` が 0 のままで、capture は `list=0` を見て拒否する。
**地形は display list を使わないので生き残る** — 利用者の「地形は見える、エンティティとプレイヤーは見えない」と一致する。

### vanilla のソースで確定した本当の根因（2026-10-15）

```
public void func_78785_a(float par1) {                  // render
    if (!this.compiled) { this.compileDisplayList(par1); }
    …
    GL11.glCallList(this.displayList);                   // ← 実際の描画はここ
}
private void compileDisplayList(float par1) {
    this.displayList = GLAllocation.generateDisplayLists(1);   // glGenLists
    GL11.glNewList(this.displayList, GL11.GL_COMPILE);         // ← GL_COMPILE（実行しない）
    for (…) ((ModelBox)this.cubeList.get(var3)).render(var2, par1);   // quad は「記録」される
    GL11.glEndList();
    this.compiled = true;
}
```

**2つの事実が決定的**:

1. **`compileDisplayList` は `GL_COMPILE` モードでコンパイルする** — quad は**描かれずにリストへ記録されるだけ**で、実行されない。
2. **実際の描画は `GL11.glCallList(this.displayList)`** で起きる。

**したがって `captureQuad` が走っている場所（`compileDisplayList` の中）は「描画」ではなく「コンパイル」である。**
そして本当の描画である `glCallList` は GL-less では stub なので、**リストの中身が再生されない**。
**これが「エンティティとプレイヤーが永久に見えない」の根因**である。

`list=0` の説明もつく: `GLAllocation.generateDisplayLists(1)`（= `glGenLists`）が stub で 0 を返すため、
`glNewList(0, GL_COMPILE)` になり `listId=0` で拒否される。観測と一致する。

### 修正の方向（本質的なもの）

**GL-less の stub に display list の意味論を実装する**:

```
glGenLists(n)             → 非ゼロの ID を返す
glNewList(id, GL_COMPILE) → 記録開始
glEndList()               → 記録終了
glCallList(id)            → 記録した quad を再生して描く   ← ここが本当の描画
```

**capture を `glCallList` 側へ移すのが正しい。** `compileDisplayList` は記録なので、そこで「描画済み」と
見なすのは誤りである。`glGenLists` が 0 を返す限り `list` は常に 0 で、拒否は永久に続く。

`TexturedQuad` / `ModelBox` / `ModelRenderer` は**エンティティとプレイヤーのモデル描画そのもの**。
`list=0`（コンパイル済み display list が無い）かつ `texture=0`（bind が 0）なので quad が拒否され、
**誰も描かない**（AGENTS.md: 拒否は fallback ではない）。**#6・#7 はこれで説明できる。**

  - **⚠️ 訂正（2026-10-15・実測）— 拒否は原因ではなかった** ✗✓✓: `dl2` と `dl3` の拒否行は**完全に同一**で、行末のセンサスはどちらも **`captured=0 refusedUnknownList=1 refusedUnknownTexture=0 refusedDegenerate=0`**。**拒否は起動時の一度きり**であり、**毎フレームではない**。そして **`captured=0` ＝ quad を一度も capture していない**。**したがって拒否はエンティティが見えない原因ではない。** display list の記録・再生と `GL_LIST_INDEX` の回答（`13b6fde31`・`8445670c8`・`90ddc7768`）は**仕様どおりの正しい実装**だが、**この欠陥の根因ではなかった**。**「1」と言うカウンタも証拠**である（AGENTS.md の「失敗するゲートは証拠」と同じ規律）。
  - **本当の signal は `captured=0`** ✓✓✓: **モデルの幾何が `VulkanModelQuadCapture.quad()` に全く届いていない**。つまり**原因は capture の後段ではなく前段** — **モデル描画がそもそも capture 経路を通っていない**。次に測るべきは「**`ModelRenderer`/`ModelBox` が呼ばれているか**」と「**`celtium$captureQuad` ハンドラが install されているか**」であり、**拒否の理由ではない**。

  - **⚠️ さらに訂正（2026-10-15）— 「1回の拒否」は「唯一の機会を逃した」だった** ✓✓✓: ログのハンドラ名（`handler$zeo000$celeritas$celtium$bindTexture`・`handler$zda000$celeritas$celtium$announceUploadedPixels`）が **mixin の merge を証明**し、**衝突警告も無い**。`TexturedQuadMixin.java:27` に `celtium$captureQuad` がある。**拒否行の call site も `captureQuad` を指している** — つまり **`captureQuad` は呼ばれたが拒否され、以後 `captured=0` のまま**である。
  - **理由は「モデルは生涯で一度しかコンパイルしない」から** ✓✓✓: `ModelRenderer.render` は `compiled` が立つと `compileDisplayList` を二度と呼ばず、`TexturedQuad.draw` が走るのはコンパイル中だけ。**そして再生は stub の dispatch を回すので `TexturedQuad.draw` を呼ばない** ⇒ **capture の機会はコンパイル時の一度だけ**であり、**その1回を拒否すれば、そのモデルは永久に capture されない**。**したがって「1回の拒否」はノイズではなく根因である。**
  - **決定的な次の測定 ✓✓**: **`-Dceltium.debug.fnCensus=true`** を付けて leg を回す。`CELTIUM_FN_CENSUS` が `glGetIntegerv` の pname 別到着数を含むので、**`0x0B33`（`GL_LIST_INDEX`）が stub に届いているか**が直接分かる。届いていれば `getInts` の分岐を、届いていなければクエリの経路（`GL11.glGetInteger` が trampoline を通るか）を見る。

  - **⚠️ 設計の確定（2026-10-15・stub 自身のコメントが明示 ✓✓✓）— 私の直近4コミットは「モデル経路を運ばない層」を対象にしていた** ✗✓: `CeltiumGlStub.install()` は `Configuration.OPENGL_EXPLICIT_INIT.set(true)` → `GL.create(installed)` で **provider を設置するだけ**で、**`GLCapabilities` を意図的に作らない**。その理由がコメントに実測付きで書かれている — 「**No GLCapabilities is built here on purpose. Measured 2026-10-15: installing one converts LWJGL3's catchable "no capabilities" exception into an uncatchable JVM abort whenever a function's address is still zero, which broke the cohort (Flare's GpuInfo.queryGpuModel calls glGetString during mod construction) while leaving the pack's own abort in place. The LWJGL3 surface is handled by CeltiumGllessNativeTransformer instead, which replaces the native methods themselves.**」
  - **したがって層の分担はこうなっている** ✓✓✓: **capability クエリ（`glGetIntegerv`×4・`glGetError`×2）だけが stub の provider を通り**（**`CELTIUM_FN_CENSUS total=6` と一致 ✓✓**）、**描画・状態・display list は `CeltiumGllessNativeTransformer` がネイティブメソッドごと置換して受けている**。**census の `total=6` は仕様どおりであり、stub の迂回ではない。**
  - **⇒ したがって `13b6fde31`・`8445670c8`・`90ddc7768`・`3a50a9b7b` の4件は、いずれも stub の trampoline 側を直しており、モデル経路はそこを通らない** ✗✓。**仕様どおりの正しい実装だが、この欠陥の経路ではない。** **次の測定は「`CeltiumGllessNativeTransformer` が `glGenLists`・`glNewList`・`glEndList`・`glCallList` をどう扱い、`compilingList` に相当する状態をどこに持つか」** ✓✓✓。

  - **🎯 修正すべき層が確定（2026-10-15・transformer を読んで ✓✓✓）**: `CeltiumGllessNativeTransformer` は `glGenLists` を特別扱いして `CeltiumGllessHint.glGenName()` で**非ゼロ ID を返す**（`:308-311`）が、**戻り値 `V` のメソッドは `switch` の `case "V": RETURN` に落ちて「何もしない」**（`:317-318`）— **`glNewList`・`glEndList`・`glCallList` はここに落ちる**。**transformer は display list を一切記録も再生もしない**し、**`CeltiumGllessHint` にリスト状態も無い** ⇒ **`compilingList` は常に 0** ⇒ **`captureQuad` は永久に `reason=unknown-list list=0` で拒否** ⇒ **`captured=0` が固定される** ✓✓✓。
  - **したがって正しい置き場所は transformer／`CeltiumGllessHint` である** ✓✓✓: **`CeltiumGlStub` は capability クエリ（`glGetIntegerv`×4・`glGetError`×2）だけを通る層であり、モデル経路はそこを通らない**。**`13b6fde31`・`8445670c8`・`90ddc7768`・`3a50a9b7b` の実装内容（記録・再生・`compilingList`・`executingList`）はそのまま使え、置き場所を移すのが次の実装**。
  - **次の実装（この単位の続き）**: ① `CeltiumGllessHint` に display list の記録・再生と `compilingList`/`executingList` を持たせる ② transformer の `V` 分岐の前に `glNewList`/`glEndList`/`glCallList` を名前で判定して hint へ委譲する ③ `GL_LIST_INDEX` のクエリは **`CeltiumGllessNativeTransformer` 側で `glGetIntegerv` を名前で判定して答える**（**stub の `getInts` は通らない ✓**）。**受入は `captured>0` と拒否の消滅を AMD/Intel の両方で確認**。

### パノラマとサブメニューの仕様（1.12.2）

メインメニューは**パノラマ**、サブメニュー（ビデオ設定など）は**dirt 背景**を使う。
利用者の #4（パノラマが無い）と #2b（ビデオ設定に背景が無い）は、この2つがそれぞれ欠けている形である。

## 共有根因の候補が1つに絞れた（2026-10-15・コードを読んで）

**「light map の view が解放され、lit batch が拒否されている」** — これで **#1・#2b・#3・#4・#6・#7・#8 の7件が1つの根因で説明できる**。

`VulkanImmediateItemPipeline` は light map の view が解放されていると、**ゼロ view を bind する代わりに batch を拒否する**:

```
[Celtium] CELTIUM_ZERO_VIEW_REFUSAL key=0x… (the light map's view has been released; the lit batch is
refused rather than binding a zero view)
```

**エンティティ・プレイヤー・雲・アイテムはすべて lit** で、**地形は自前の経路を持つので生き残る** — 利用者の
「地形は見える、それ以外が見えない」と完全に一致する。

`VulkanModelQuadCapture` は3つの理由で quad を拒否し、**理由と call site を印字する**:
`REFUSED_UNKNOWN_LIST` / **`REFUSED_UNKNOWN_TEXTURE`** / `REFUSED_DEGENERATE`。

**そして解放している箇所が teardown 経路にある**:

```java
if (this.lightmapTexture != null) { this.lightmapTexture.delete(); this.lightmapTexture = null; }  // :9969
destroyFramebuffer();   // :9985 — #286 が settleGpu を足した経路
frameTarget.delete();
```

**#286 はこの経路に `settleGpu`（`vkDeviceWaitIdle`）を足した。** それが teardown を毎フレーム側へ引き寄せた
（あるいは順序を変えた）なら、**light map がフレームの途中で消え、以後の lit batch がすべて拒否される**。

**確定に必要なのは利用者のログのこの2行**:
1. `CELTIUM_ZERO_VIEW_REFUSAL` — **出ていれば lit batch が拒否されている**
2. `CELTIUM_MODEL_QUAD_REFUSED reason=…` — **どの理由で拒否されたか**（`UNKNOWN_TEXTURE` なら #1 も説明できる）

**推測で直さない。** この2行を読んでから、`settleGpu` の位置を `:9985` に限定する修正を入れる。

## #2a の訂正（2026-10-15・vanilla ソースで確定）

**「blur がかからない」は Celtium の欠陥ではない。vanilla 1.12.2 には blur が無い。**

vanilla の `GuiScreen.func_146270_b`（= `drawWorldBackground`）は、world があるとき
`drawGradientRect(0, 0, width, height, 0xC0101010, 0xD0101010)` を引くだけで、**ぼかしは一切しない**。
world が無いときは `options_background.png` を 32px でタイルし `0x404040` で塗る。
利用者のスクリーンショットの暗いグラデーションは**この仕様どおり**である。

ぼかしは **`tterrag1098/Blur` という別 Mod の機能**で、利用者の 16 mod 構成には入っていない。
したがって **#2a は「入っていない Mod の機能を期待している」**であり、修正対象ではない。
**記録から欠陥として数えない。**

一方 **#2b（ビデオ設定で暗幕すら無い）は実バグ**として残す。

## #5 の見立て（利用者の要求どおり、原理的に可能かを明示する）

**原理的に不可能ではない。** ただし経路が2つあり、どちらなのかを先に確定させる必要がある。

- Cleanroom の起動ロゴは `SplashProgress` 系（Forge 由来）で、**GL で描く**。GL-less 経路には GL context が無いので、そのままでは描けない。**これは「描けない」ではなく「native pass がまだ無い」**。
- 一方で「**表示されない**」という観測は、**描画が失敗している**のか **そもそも呼ばれていない**のかを区別していない。Cleanroom は `SplashProgress.finish()` を早期に呼ぶ経路があり、それが走っていれば**描く機会自体が無い**。

したがって次の順で確定させる:
1. ログに `CELTIUM_SPLASH_HOOK` が出ているか（既存の計器。出ていれば hook は呼ばれている）
2. `SplashProgress` の描画が native pass を持っているか
3. 上記2つで「呼ばれていない」なら**原理ではなく起動順序の問題**であり、修正可能

**「不可能」と断定するのは、1〜3 を測ってからにする。** 現時点で断定しない。
