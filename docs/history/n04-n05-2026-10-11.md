# N04 + N05 — fix, acceptance runs and unapplied work (2026-10-11)

Scope: audit `docs/history/2026-10-11-full-audit-0903.md`, findings **N04** (bridge post chains run on empty
pure-Vulkan stand-ins) and **N05** (recorded layouts/initialization committed by a submission that did not carry
them). Owner of record for this work: `VulkanPostChain.java` (+ `ShaderGroupMixin.java`); the commit hook in
`VulkanTerrainGpuBackend.java` and the layout ledger in `VulkanGlTexture.java` belong to other agents — the patch
texts written for them are in `.celtium-work/patches/` and their state is noted below.

## 1. What the source actually did

### N04 — the input of a chain was never checked

* `VulkanTerrainGpuBackend.adoptChainFramebuffers` (now `:6433`) returns immediately when
  `offTargetTarget() == null`, i.e. for every GL-bridge configuration: "The GL bridge has real GL framebuffers behind
  these identities; there is no stand-in image to adopt." Under the bridge nothing was ever adopted, so
  `postAdopted=0`.
* `VulkanPostChain.target(int fbId, int w, int h)` (now `:~820`) allocated a fresh `R8G8B8A8` image + framebuffer for
  every identity the pass list named and the class had not seen — including the chain's *input* framebuffer, which
  under the bridge is a real GL framebuffer the renderer has no Vulkan image for.
* The old `checkStandInTarget` (`:647-670` before this change) noticed exactly that case, incremented
  `runsOnAllocatedStandIn`, printed one line, and then **let the chain run anyway** — so the first pass sampled an
  image that was still `UNDEFINED` (transitioned by the chain's own barrier) and the chain's output went to an image
  nothing outside the chain reads. That is the "postRunsOnStandIn" the audit measured.
* The GL-less adoption path (`adoptChainFramebuffer`, now `:6451-6480`) does supply a real image: it requires
  `framebufferColorTexture(identity)` — the association the game's own `Framebuffer.bindFramebuffer` reported — and
  the renderer-owned off-target pair the silhouette was drawn into, cleared once per frame generation
  (`GllessFrameTarget.clearOffTarget`), then publishes it under the GL texture name the composite binds. That path is
  what the audit's `postAdopted=1 postRunsOnStandIn=0` measured.

### N05 item 1 — the commit was tied to a foreign submission

* `celtium$postChainRun` set `postChainCommitPending = true` right after `recordPasses` and *before*
  `submitCommands()` (old `:6243-6244`), while the actual `postChain.commitPasses()` ran in the **terrain pass**
  success path (`render(...)`, old `:549-555`). A chain command buffer that was reset, abandoned or refused
  therefore had its first-use barriers marked "fact" by the next successful terrain submission. The direction that
  was supposed to work was unreliable too: in the reproduced bridge run with the old jar, 43 chain recordings were
  committed by the terrain path **zero** times (`postRecordingCommits=0`, `postUncommittedRecordings=42`,
  `postRepeatInits=84`), i.e. every recording re-recorded both barriers.
* The fix is the token: `recordPasses` returns the recording's token, `commitPasses(int)` commits only the pending
  set of that token, and the caller commits immediately after *its own* accepted `vkQueueSubmit`.

### N05 item 2 — `VulkanGlTexture` recorded the layout as fact before the submit

* The audited code (`transitionForeignLayout`, old `:541-573`) ended with `this.foreignLayout = newLayout;`
  immediately after `vkCmdPipelineBarrier`; a recording, release or submit failure then left the wrapper believing the
  image had moved, so the next `ensureGeneralLayout`/`ensureSampledLayout` could skip a barrier the image still
  needed.
* **In the working tree this has been replaced by the texture-batch owner** with a per-image shared fact
  (`ForeignLayoutState`, `FOREIGN_STATES`) plus a per-command-buffer recording ledger (`LayoutRecording`,
  `RECORDINGS`): `recordForeignTransition` (`VulkanGlTexture.java:634`) registers the pending transition *after* the
  barrier is recorded and only `commitLayoutRecording` (`:449`) moves the confirmed layout; `abandonLayoutRecording`
  (`:491`) drops it; the three wrappers of one image share one fact. That is the audit's contract.
* It was **inert** when I read it (no caller: every transition took the `recording == null` branch at `:597-621` and
  set `state.confirmed = wanted` at record time, counted as `foreignLayoutUnbound`). The caller-side patch I wrote
  (`.celtium-work/patches/n05-layout-recording-caller-VulkanTerrainGpuBackend.patch`) has since been applied by the
  owner: `beginLayoutRecording` in `beginCommands()` (`VulkanTerrainGpuBackend.java:7214`), `commitLayoutRecording`
  right after the successful `vkQueueSubmit` (`:7686`), `abandonLayoutRecording` in the post-chain failure path
  (`:6392`). A run whose `foreignLayoutSummary()` shows `unbound=0` has the binding in effect.

## 2. What changed (this work)

`celtium-vulkan/.../VulkanPostChain.java`

* class contract documented: a chain is accepted only when every image it reads from outside itself is suppliable
  (class javadoc, `:~74-87`).
* `unsuppliedInput(List<Pass>)` (`:673`) + `unsuppliedInput(int, Pass, Set, boolean, int, int, int) ` (`:700`): walks
  the pass list in order; an input is suppliable when it is the group's main framebuffer, an image the caller
  adopted (`targets` holds it as non-owned), or a target an earlier pass of the same chain wrote. Anything else is
  refused with a reason naming pass, program, identity and size.
* `recordPasses` (`:414`) now returns the recording token, refuses an unsuppliable chain with
  `UnsuppliedInputException` (`:786`) **before anything is recorded**, and re-records the barriers of targets whose
  earlier recording was never committed (`:417-440`, `postUncommittedRecordings`/`postRepeatInits`).
* `commitPasses(int recordingToken)` (`:574`): commits only the recording that owns the pending set; a token naming
  any other recording is counted as `postStaleCommits` and commits nothing. `commitPasses()` (`:598`) is kept as
  "commit the pending recording" so an unpatched caller keeps the re-record-on-abandon behaviour, documented as the
  non-contract form.
* `status()` (`:755`) adds `postRefusedUnsuppliedInput`, `postStandInRefusals`, `postStaleCommits`;
  `postRunsOnStandIn` is now structurally zero (a stand-in run cannot happen).
* test-only injection `-Dceltium.vulkan.postChainFailFirstUse=<n>` (`:209`, `:545`), active only together with
  `-Dceltium.vulkan.validation=true`: throws after the recording is complete and before the caller's submit, which is
  the audit's acceptance point. (The permanent answer is the token, not the flag.)

`forge122/.../ShaderGroupMixin.java` (`:60-70`)

* a group whose main framebuffer is not the game's own no longer runs natively: every "main" pass would otherwise
  resolve to the shared frame image and read/write the wrong image. Vanilla builds groups with
  `mc.getFramebuffer()` (`RenderGlobal.makeEntityOutlineShader`, `EntityRenderer.loadShader`), so this is a guard
  around a hole, not a behaviour change in the measured scenes.

### N05 fail-once acceptance

Scene: the fixture's spectator effect (`-Dceltium.validation.spectator=enderman` → `EntityRenderer.loadEntityShader`
loads `shaders/post/invert.json`, two passes: `invert` main→owned target, `blit` owned target→main). This is a chain
whose real input *is* suppliable, so it is accepted and records; the bridge glow chain cannot be used for this
acceptance because it is refused (that is N04's fix).

The injection (`-Dceltium.vulkan.postChainFailFirstUse=1`, validation-gated) fails the first recording after it is
fully recorded and before the caller's `vkQueueSubmit`.

|---|---|---|---|---|---|---|---|---|
| `n05-accept-ctl` (no injection) | 70 | 140 | 1 | 70 | 0 | 0 | 0 | 0 |
| `n05-failonce` (injection, before the command-state reset) | 0 | 2 | 1 | **0** | 0 | 0 | 0 | 0 |
| `n05-failonce-glless` (injection, GL-less, before the reset) | 0 | 2 | 1 | **0** | 0 | 0 | 0 | 0 |
| **`n05-failonce2` (injection, after the reset)** | **59** | 120 | **2** | **59** | **1** | **1** | **0** | 0 |

Control run, the healthy shape: `run=0 recording=1 passes=2 pendingInit=1` with
`initBarrier recording=1 identity=... owned=true`, then 69 further recordings with `pendingInit=0` — one barrier ever
recorded, and `postRecordingCommits=70`, i.e. one commit per accepted chain submission. The foreign-image layout
ledger agrees: `layout[transitions=0 skips=0 commits=70 abandons=0 dropped=0 open=0 unbound=0]`.

`n05-failonce2` — the acceptance, after the owner added the command-state reset
(`.celtium-work/patches/n05-command-state-on-post-chain-refusal.patch`):

```
CELTIUM_POSTCHAIN initBarrier recording=1 identity=1676649052 ... owned=true barriersForThisTarget=1
CELTIUM_POSTCHAIN run=0 recording=1 passes=2 pendingInit=1
CELTIUM_POSTCHAIN pass=0 program=invert in=main(1280x720) out=owned#1676649052(...,initialized=false)
CELTIUM_POSTCHAIN pass=1 program=blit in=owned#1676649052(...,initialized=false) out=main(1280x720)
CELTIUM_POSTCHAIN INJECTED_FAILURE recording=1 pendingInit=1 - recorded, never submitted; the next recording must
  carry these barriers again (injected=1/1)
CELTIUM_POSTCHAIN UNCOMMITTED identity=1676649052 ... recording=1 (committedRecording=1): its UNDEFINED -> GENERAL
  barrier was recorded but commitPasses(1) did not report that recording as submitted, so it is recorded again here
CELTIUM_POSTCHAIN initBarrier recording=2 identity=1676649052 ... owned=true barriersForThisTarget=2   <- re-recorded
CELTIUM_POSTCHAIN run=0 recording=2 passes=2 pendingInit=1
CELTIUM_POSTCHAIN run=1 recording=3 passes=2 pendingInit=0
CELTIUM_POSTCHAIN run=2 recording=4 passes=2 pendingInit=0
```

* The failure lands exactly where the audit asks: the first-use barrier and both draws are recorded
  (`pendingInit=1`), the recording is never submitted, and the queue never owns it.
* **The next successful buffer re-records the barrier it needs**: `recording=2` carries
  `initBarrier ... barriersForThisTarget=2` and is the recording that gets committed
  (`postRecordingInitBarriers=2, postRepeatInits=1, postUncommittedRecordings=1`).
* **Nothing else is disturbed**: the target set is unchanged (`postTargets=1`, one creation), every recording after
  the recovery has `pendingInit=0`, `postStaleCommits=0`, no foreign-layout transition was invented
  (`layout[... transitions=0 ... unbound=0]`), the renderer kept its frame rate (236 world frames against the
  control's 205; the earlier run's 55 and the six `nested begin` failures are gone), and VUIDs stayed 0.
* **Another buffer's success never commits it**: the refused recording's commit count is 0 - the terrain path no
  longer touches the chain - while the 59 accepted chain submissions commit exactly once each
  (`postRecordingCommits=59`).
* The run's picture verdict is `FAILED_PRESENTED_IMAGE`, which is expected and unrelated: the effect under test is
  `invert.json` (the screen is inverted), and the same tree currently fails the scene gate on the unrelated terrain
  shard/depth defect (see N06).

## 6. What remains unproven

* A GL-less glow run with this build. The current tree's GL-less scene renders large flat shards (the audit's N06)
  and never reached the post-chain executor in three runs (`n04-glless`, `n04-glless-fail`: 23-149 world frames,
  `postChains=0`), which is unrelated to this change - the GL-less runs' own counters show the adoption path never
  ran at all (`postAdopted=0`) because the outline group was not drawn. The audit-era GL-less evidence
  (`postChains=43 postAdopted=1 postRunsOnStandIn=0`) shows the adoption path as it was measured, and the gate
  accepts an admitted identity by construction (`unsuppliedInput` returns null for a non-owned target, which is
  exactly what `adoptTarget` installs), but I have not re-run the GL-less glow end to end on this build.
* The glow picture itself (outline presence/quality against the Celeritas/GL reference). The bridge evidence is
  confounded by the unrelated terrain shard/depth defect: `n04-bridge2`, the same build, fails the picture gate with
  `postChains=0` and `nonBackground=0.2593`, so the picture verdicts in this scene cannot be attributed to the post
  chain. The picture gate's weakness itself is N06.
* A chain whose *output* is an owned target nothing outside the chain reads is still accepted (the gate is on
  inputs, per the audit's N04 wording). The measured glow chain writes its last pass into the adopted image, so it
  is unaffected; a main-input chain that ends in a private target would be accepted with its result invisible.
* The fail-once acceptance injects the failure at the end of `recordPasses` (fully recorded, never submitted) rather
  than through a refused `vkQueueSubmit`; the state the chain sees is the same (a recording the queue never owned),
  but the driver-refusal path and any device-lost interaction are not exercised here - deliberately, since the audit
  forbids the reset/free-after-device-loss test.
* B(2)'s GPU evidence is the owner's, not mine: my runs only observed the ledger's wiring
  (`layout[transitions=0 skips=0 commits=59 abandons=1 dropped=0 open=0 unbound=0]`). No run here forced a *foreign
  image* transition to be dropped mid-recording, so the "unbound=0 plus a real drop-and-re-record of a foreign
  image" case is still to be seen.
