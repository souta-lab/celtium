## Device selection — it works, and what pins it

- `intel-glless` report: `nativeDeviceName="Intel(R) UHD Graphics 630 (CFL GT2)"`, uuid
  `8680923e000000000002000000000000`, `nativeDeviceMatchedOpenGl=false`, `driver.vulkanDeviceCount=1`,
  `deviceType=1`, `gpuRequirementSource=nativeDeviceName`, `gpuRequirementMet=true`.
- `intel-ref` report: `glRendererPreflight="Mesa Intel(R) UHD Graphics 630 (CFL GT2)"`,
  `gpuRequirementSource=glRendererPreflight`, `gpuRequirementMet=true`.
- **`VK_ICD_FILENAMES` is the pin, not `--render-node`.** `VulkanContext.matchPhysicalDevice` takes the
  first non-CPU Vulkan 1.2 device when there is no OpenGL identity to match against
  (`VulkanContext.java:740-790`), so with the ICD pinned the enumeration holds one device and the first is
  the Intel one; unpinned it holds three (`plan.md:63`: `vulkanDeviceCount 1` pinned vs 3 unpinned). The
  `--render-node` argument only points the headless compositor at the same iGPU, which is also why
  `glRendererPreflight` in the GL-less report is the stub's own name and says nothing about the GPU — the
  `CELTIUM_NATIVE_DEVICE` line is the one that does.
- `matchedOpenGl=false` is the honest form of "the pin was the only thing choosing this device": no run in
  this configuration matches a GL UUID, so a run with the ICD unpinned would silently measure whichever
  device `vkEnumeratePhysicalDevices` listed first. Nothing had to change in `VulkanContext` for this leg.

## What differs between the vendors, and what is still unverified

**Differs, measured:** nothing in the GL-less frame beyond rasterisation noise — 0 pixels over 8 in rows
0-200 (max 1 count) and 4 pixels over 8 in rows 260-720. Both vendors pick `D32_SFLOAT` as candidate 1 of 6,
both accept every layout offered except one format-2 batch, both report 0 skipped terrain sections, 0 VUIDs,
and identical device-selection behaviour (`matchedOpenGl=false`, ICD pin required). The capability-based
pieces that could have diverged — the depth-format chooser and the format table — did not diverge on this
pair of devices; the *reason* they are capability-based (AMD has no 24-bit depth format, Intel no
`D16_UNORM_S8_UINT`) is untouched by this run because neither fallback was reached.

**Unverified on Intel (not claimed):**
- The **stars and the horizon plane** on Intel, for the same fixture reason as AMD: `WorldType.FLAT` makes
  `World.getHorizon()` 0.0 so the horizon plane's `d3 < 0` branch never runs, and `worldTime` pinned to 6000
  makes the star brightness exactly 0 so the star draw does not exist in the captured frame. The decode is
  the same code path on both vendors, but neither vendor's *picture* contains those two stages.
- **The fallback depth candidates** (`D24_UNORM_S8_UINT`, `D32_SFLOAT_S8_UINT`, `X8_D24_UNORM_PACK32`,
  `D16_UNORM_S8_UINT`, `D16_UNORM`) on either vendor: only candidate 1 was reached here.
- **Resize, device loss, multi-GPU, suspend/resume** on Intel, and **every vendor/OS other than AMD and Intel
  on Linux** — unchanged from `plan.md`'s statement.
- **The GUI/item/entity stages on Intel beyond the panel scene**: the panel pair above covers the inventory
  and JEI panel with the world behind it, but no entity scene, no TESR scene, no resize and no
  block-breaking/selection stage was taken on Intel. Nothing here says those work on the Intel driver.
- **Frame pacing / performance** on Intel: not measured; this is an acceptance leg, not a benchmark.
- The two legs ran on **different celtium jars** (Intel `bf5a4e14…`, AMD task-3 `a106e84a…`) and different
  run lengths (203 vs 207 ticks), so the cross-vendor frame comparison is between two different builds of the
  same tree rather than one jar. Within each vendor the candidate-vs-reference comparison is same-fixture,
  same-pose, same-tick, which is the comparison the acceptance needs.
