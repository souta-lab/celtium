### N01 — model頂点の上書き: 原因確定、監査中に修正

VulkanTerrainGpuBackend.celtium$buildModelMeshes、5880–5893:

~~~java
for (int quad = 0; quad < quadLimit; quad++) {
    int base = mesh.nextVertex();
    for (int vertex = 0; vertex < 4; vertex++) {
        mesh.putPosition(...);
        mesh.putUv(...);
    }
    // base, base+1, base+2 / base, base+2, base+3
}
~~~

VulkanDynamicMesh.nextVertex()は一つの頂点を開始し、putPosition/putUvはその「最後の頂点」へ書く。上記は四隅を同じ頂点に書き、Q個のquadからQ個のvertexしか作らない。indexの最大値はQ+2となり、書いた頂点の上限Q-1を超える。余分なbuffer容量があっても、その範囲に正しい頂点を書いたことにはならない。GPU Validationが0でもgeometryは壊れる。

A jarのjavapでもnextVertexはbytecode158、inner loopは166に始まり、putPosition213 / putUv250、256から166へ戻る。inner loopにnextVertexがないことを確認した。巨大な半透明片や黒いtriangleをmatrix/depthだけで修正し続ける根拠はない。

先行送信後、454fb3600cb80e2368d2f18d2e3cf2f1879227a9でnextVertexをinner loopへ移し、4Q vertices / 6Q indicesの契約を追加。C jarではnextVertex174がloop内にあり、309から166へ戻り、vertexCount/indexCountの検査も収録されている。

p1-model-fixとp1-intelは同じC jarでclean/0、巨大な片が消えることを目視した。**閉じたのはこの頂点構築不具合。全modelの照明/texture/射影/寿命/見た目ではない。** commit説明のpitch20に対して実JSONのcameraはpitch-14だった点はN06/N13として残す。

先行queueのrequestId: 7aa6a440-0642-4415-81a0-6bd4395ab733。accepted=true、inboxのtag/requestIdを確認し、その後消費された。tag: CELTIUM_AUDIT_20261011_URGENT_MODEL_VERTEX_CX。

### N02 — model meshの寿命、再compile、resource reload

VulkanTerrainGpuBackend.celtium$buildModelMeshes、5843–5903は、list数が増えるたびに**全listのmeshを再作成し、modelMeshesを新mapへ置き換える**。旧mapのmeshをdelete/retireする処理はない。backend全体のmodelMeshes参照を検索しても、解放処理は見つからなかった。途中で例外になった新mapも解放されない。

さらに更新判定がmap.size() >= listIds.lengthだけなので、**同じlist IDの再compileや内容変更は新meshへ反映されない**。VulkanModelQuadCaptureのLISTSにもcompile開始時のgeneration/resetやdelete時のremove/clearが見当たらず、再compileでは旧geometryへ追記され得る。

各VulkanDynamicMeshは最低64KiBのvertex bufferと32KiBのindex bufferを作る。逐次list追加の場合には再構築量が累積する。これはCPU負荷とGPU/host-visible memoryの両方の問題で、少数のmodelでfixtureが通ることでは閉じない。

修正は、list IDにresource/compile generationを持たせ、変更したlistだけ再構築し、旧meshを実際のGPU完了後にretireする。compile開始、compile完了、delete、reload、world/backend終了を同じ所有契約に揃える。作成失敗の新mesh群も回収する。

受入は、小さなmodelの追加、同じIDの再compile、delete/reuse、reload/world切替でgeometryが更新され、旧bufferのlive数が元へ戻ること。全entityを個別に特殊対応する方式には広げない。

### N03 — 文字描画はまだnative経路へ届いていない

CeltiumGlStubはglBegin、glEnd、glVertex3f、glTexCoord2f等をno-opとして登録している。一方、1.12.2 FontRendererのdefault/unicode glyphはその入口を使う。WorldVertexBufferUploaderへのoffer hookだけでは、FontRendererのこの描画を捕捉できない。締切のC jarにFontRenderer/GluProjectionのMixin classは収録されていない。

実画像でも、mod6-bridge-hudmodsのchat、tutorial toast、MapWriter座標の文字は、mod5-hud-modsのGL-less画像から消えている。JEIのアイコンがあるmod2-glless-pic2でも、文字やsearch fieldの表示を正常なJEI画面として受入できない。hideGUIで文字を隠した通常fixtureを根拠にはしていない。

**これは既存modに入る前に、vanilla font/UIの未完でもある。** format受付率にこの文字は入らない。item-layoutの100%受付は文字やGUI完成を意味しない。

FontRendererの意味のある入口からglyph、unicode、色/alpha、shadow、advance、textureをnative batchへ接続し、公開APIの戻り値と位置計算を保つ。GL全APIの汎用変換器を作らない。比較は普通のASCII/日本語/装飾/影つき文字とchat、inventory、JEI等を少数の固定sceneで行い、native glyphの提出/完了と実画像を確認する。

DSHの公開発言で専用担当が着手したことは確認した。着手を修正済みの受入にはしていない。

### N04 — bridgeのpost chainが空のstand-inを入力にする

VulkanTerrainGpuBackend.adoptChainFramebuffers、6204–6209はoffTargetTarget()がnullのbridgeでadoptionを行わない。VulkanPostChain.target、633–653は未登録の非main FBOを新しいpure-Vulkan targetとして作る。しかし、そこへ元のGL silhouette/inputを供給する処理をこの経路では確認できない。

intel-layout-glowではpostChains=19、postPasses=76、postAdopted=0、postRunsOnStandIn=19、黒率78.6554%、画像FAIL。GPU Validationの0は、正しい入力を読んだ証拠にはならない。

GL-less側には実silhouetteをadopt/publishする実装が入っているが、bridgeの外部FBO入力まで同じ契約になったとはいえない。glowの存在や画質も未受入。

まず入力の供給元を確認できるchainだけ受理する。bridgeで実入力がnativeに渡せないchainは、実GL contextがある間はそのGL chainへ正しく戻す。空の代用品で成功としない。GL-lessでは、MC framebufferのidentity/generationから、実際に描いたnative imageを採用する。汎用GL framebufferエミュレーションへ拡大しない。

受入は、silhouette入力、各中間target、最終outline合成の対応と、元Celeritas/GL参照の正しい発光画像。単なるpostPasses増加では閉じない。

### N05 — recordしたlayoutと、実際にsubmitしたlayoutが一致しない失敗経路

二つの契約不足がある。

1. celtium$postChainRun、6163–6174はrecord後にpostChainCommitPending=trueを設定してsubmitするが、commitPasses()はこのsubmitの直後にない。545–550の別のterrain render成功時に確定する。チェーンを含むcommand bufferをsubmitできずに捨て、次のterrain submitだけ成功しても、未実行のchainの初期化をcommitできる形になっている。
2. VulkanGlTexture.transitionForeignLayout、541–573はbarrierをrecordした直後にforeignLayout=newLayoutとする。post記録、release、submitが途中で失敗してbufferを捨てても、bookkeepingは実imageが移動したと思う。次のensureGeneralLayout等が必要なbarrierをskipできる。

通常glow runのpostUncommittedRecordings=0やclean/0は、失敗後の正しさを証明しない。今回GPUへfaultを注入して再現したとは主張しない。sourceのcommit位置と破棄後の経路から確認した契約不具合である。

記録中のpending layout/初期化をcommand bufferまたはsubmission tokenに結び、**そのsubmitがqueueに受理された時だけ**確定する。reset/abandon/submit拒否では未確定分をrollbackまたは再記録し、別bufferの成功でcommitしない。owned/adopted/published wrapperが一つのlayout事実を共有する。

限定受入は、postのfirst-useを記録後・queue所有前で一度失敗させ、次の成功bufferが必要なbarrierを再記録することと、他のtarget/stateを壊さないこと。実device loss後に危険なreset/freeを行う試験にはしない。

### N06 — 画像ゲートが「正常描画」の判定として弱い

Aのw2-baseやglow-bridge5は画像ゲートPASSだが、実画像には巨大な破片や黒いshardがある。colour count、non-background、row bands、黒率は、単色/大規模な黒画面を弾く計器にはなるが、geometry/文字/outlineの正しさを保証しない。

### N07 — animated spriteのmip更新がlevel0だけ

VulkanTextureRegistry.applyAnnouncedTo、814–826はdataをlevel0へ変換し、部分patchではuploadPatchFromPixelsを呼ぶ。VulkanGlTexture、859–876はlevel0だけへcopyする。copyToImageのpreserve経路はそのlevelだけを更新し、mip chainを再生成しない。samplerはhigher mipへ到達できる。

初回全面upload後にspriteが動いても、遠景で使うlevel1以降が初回のままになり得る。water/lava/fireなどのanimationで、近景と遠景の位相や見た目が分かれる契約である。今回その専用GPU場面は追加していない。

MCが供給したint[mip][flat]を利用するか、正しい領域のmipを更新する。隣接spriteやpatch外を保ち、全atlasの再upload/queue drainへ退行させない。更新level、領域、generation、descriptorが実際にsampleするimageへ揃うことを確認する。

### N08 — ByteBufferのhash起点、転送長、入力検査

uploadFromImage、880–902はrgba.get(i)でindex0からhashを作る。一方、copyToImage、1626–1692はMemoryUtil.memAddress(pixels)からwidth*height*4 bytesをcopyする。memAddressは現在のpositionを使う。

positionが非0なら、hashと転送は違うデータを表す。positionより前が同じでpayloadだけ変わった入力を、古いhashの重複としてskipできる。またhash側はremainingから小さなstrideを作るが、転送側は要求サイズを読み、remaining不足を拒否していない。短いdirect bufferではJavaの境界検査を越えたnative readになり得る。

正のextent、overflowを検査した必要byte数、direct buffer、remaining>=必要byte数を入口で確認し、positionから同じsliceをhash/転送する。callerのposition/limitは変えない。CPU側の契約は、非0position、内容変更、short buffer、overflow、exact-sizeで検証する。

現在の内部announcementはpos0のbufferを作るため、全通常runでこの不具合が発生しているとはしていない。

### N09 — state hook失敗の黙殺

GlStateManagerMixin.celtium$mirror、409–420はaction.acceptをcatch(Throwable ignored)で無視する。GL-lessではその後のGL bodyもno-opなので、失敗したstateはどこも反映しない。

新しいstubのtransform censusは、正しくmirrorした呼出しのGL bodyも数える**arrivalの分母**である。失敗したhookを特定する計器ではない。matrixMirrorDeltaもstubがmirror自体を返す構成では独立したGL参照にならない。

hook失敗の名前/回数と、stateを確定できないdrawの明示的な拒否を用意する。require=0の重要なentryには、実際に適用されたことの確認を残す。未取得の行列やhook不在をidentityとして成功にしない。GLUの新しいdirty Mixinは締切の実行物にはなく、専用受入待ちである。

### N10 — 全GPUへ向けた能力契約に残る固定条件

### N14 — 全経路のbounded waitはまだ証明されていない

### N15 — censusの分母と意味

AではimmediateOfferedByFormatが8要素だったため、format8/9がoffered tableに出ない。締切までにソースはVulkanImmediateFormats.COUNTへ修正された。これは旧ログへ遡及させない。

他にもoffers/accepted/censusは異なるcadenceでprintされ、backendなし等でoffer前に戻ってもGL bodyは計上される。このため単一の古い行からacceptedとglBodyCompletedを引き算して割合を出すと閉じない。

GL-lessのglBodyCompletedはstubの本体が走った回数であり、GLが描いた回数ではない。FontRendererなど、そもそもofferへ来ない経路も存在する。画面自身の不要なblit拒否と、必要なparticleの欠落も区別する。

同じ区間と同じlifetimeでoffered/accepted/queued/recorded/submitted/completed/droppedを出し、never-offeredを別に計測する。call countの比率はGPU時間/画素/機能coverageの比率ではない。

particle descriptorのlastUiPass=null問題は1e08cfd60でstandalone passの選択へ直り、B/CのparticleDescriptorRefusals=0を確認した。これをfontや全particle表現の完成へ拡大しない。

### N16 — post descriptor ringの容量

VulkanPostChainはsetRing=32、descriptorSet()はround-robinでvkUpdateDescriptorSetsする。一方supportsAll()にpass数の上限検査がない。

同じcommand bufferの33番目以降で、既に記録したdrawが参照するsetへ回り、前のdescriptorを上書きできる。普通のvanillaの4pass等で発生したと主張するものではない。MC ShaderGroup APIの利用者が長い対応programのchainを組んだ際に、受理したまま誤描画/invalid recordingになり得る。

必要set数をpreflightで確保するか、容量を超えるchainを理由つきで記録前に拒否する。record中に既使用setを更新しない。複数aux samplerやresourcepackによるprogram内容変更も、名前だけで同じnative programとみなさず、対応範囲を明確にする。

### N17 — host buffer作成失敗の解放漏れ

VulkanHostBuffer.create、105–137はvkCreateBufferでhandleを作り、その後memory type選択、allocation、bind、mapを行う。catch/finallyによる部分解放がない。126のallocation faultではbufferを作った後に例外になり、constructorから戻らないのでcallerはそのobjectをdeleteできない。

DynamicMeshでもvertex buffer作成成功後にindex buffer作成が失敗した場合の回収がない。N02の途中作成mapとも関連するが、constructor自体の契約を直す必要がある。

部分作成のownerを一つにし、作成が完了しない場合は作成済みhandle/memoryを解放する。GPUへ提出していない資源の解放と、pending資源のretireは分ける。限定fault受入は、failure counterやfixture終了だけでなく、生成/破棄/live handleの差が元へ戻ることを確認する。
