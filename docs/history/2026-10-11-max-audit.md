## F01 — 表示リストの GL 描画は止まっていない

対象: forge122/src/main/java/org/taumc/celeritas/mixin/core/GlStateManagerMixin.java:39–76。

callList の @Inject に **cancellable=true がない**。drawn=true の場合に census.cancelled(list) を増やし、続いて info.cancel() を呼ぶ。
CleanMix 0.7.2 の実 CallbackInfo.cancel は、cancellable=false なら CancellationException を投げる。この例外は RuntimeException で、外側の catch が飲み込む。
Mixin の annotation の既定値 false も、実 CleanMix jar と実行 jar で確認した。

したがって、カウンターは取消済みに見えても、元メソッドへ戻って GL の list 呼出しが続く。bridge では二重描画の可能性があり、GL-less では stub に落ちる。カウンターは GL 経路を排除した証明にならない。

修正・受入:
1. 正しい注入に cancellable=true を指定する。カウンターは実取消の成立後に更新する。
2. cancellation 自体の例外を「計測なので無視」の catch に隠さない。
3. native draw 成功時に元 GL 本体が実行されないことを測る。draw 不成立時は bridge の明示 fallback と GL-less の未対応を区別する。
4. WorldVertexBufferUploaderMixin は既に cancellable=true を持ち、この原理をコメントにも書いている。同じ契約を model 側にも適用する。

一次資料: [CallbackInfo](https://github.com/SpongePowered/Mixin/blob/master/src/main/java/org/spongepowered/asm/mixin/injection/callback/CallbackInfo.java)、[Inject](https://github.com/SpongePowered/Mixin/blob/master/src/main/java/org/spongepowered/asm/mixin/injection/Inject.java)。実環境の逆アセンブルでも照合済み。

## F02 / F03 — 行列フックの修正と実行物を一致させる

対象: GlStateManagerMixin.java:179–181 / 230–232（固定 HEAD）。

既存は translate(double,double,double) と scale(float,float,float) のみ。
抜けた overload:
- func_179109_b(FFF)V — translate(float,float,float)
- func_179139_a(DDD)V — scale(double,double,double)

MC 1.12.2 実 client jar の obfuscated bus を逆アセンブルすると、float translate は glTranslatef、double scale は glScaled を直接呼ぶ。既存 hook の overload に委譲しない。
GL-less stub はこの状態変更を no-op にするため、native mirror はこれらの変更を見ない。手持ち・entity・TESR 等の変換不足を説明する具体的な原因である。個別モデルを特例修正する必要はない。

旧 GL-less run は modelMatrixPair の compile/replay translation が (0,0,0)、一方 bridge は非ゼロだった。
ただし画像の大きな前景すべてをこの原因だけで説明したとは断定しない。固定 camera の比較が必要。

作業中ソースには両 hook の追加がある。しかし **translate-fix2 / announce-fix-g / outline2 の本体 jar を javap -p で確認すると、celtium$translateFloat / celtium$scaleDouble が存在しない**。
translate-fix2 の translateCalls=40 は worldFrames=40 で、追加 hook の実働証拠にもならない。

修正・受入:
- worker の統合後、一つの確定したビルドから jar を作る。追加メソッドと注入 descriptor を実 jar で確認し、各 run に jar hash を残す。
- その同じ jar を AMD/Intel × bridge/GL-less で使う。固定 camera・同じ TESR/手持ち場面で比較する。
- 必須 hook が注入されたことを検査する。require=0 により不成立が黙って通る状態を受入の根拠にしない。
- GL-less の matrixMirrorDelta=0 は、stub の glGetFloatv が同じ mirror を返す自己比較である。独立した正解の証明ではない。

なお color(float,float,float) は実 bytecode で color(float,float,float,float) に委譲する。こちらは追加 hook 不足として扱わない。

## F08 — diagnostic readback に境界条件が残る

対象: VulkanTerrainGpuBackend.java:5263–5274 / 7446–7451、VulkanArena.java:270–271。

条件は offset + commonVertexStride <= arena.capacity。一方 vkCmdCopyBuffer は固定 64 byte。
stride=32 なら末尾 32 byte があるだけで条件を通り、64 byte copy は buffer 外に出得る。arena の deviceAllocatedMemoryL は memory requirement の余白ではなく実 buffer capacity だった。

64 byte の実 copy 範囲を検査するか、必要 byte 数を安全に縮める。拒否した slot を readBackAndLog が未書込みデータとして数えないよう、有効 slot を追跡する。
今回の region-per-slot 修正は有効だが、境界の是正が全部終わった証明ではない。

## F09 — ByteBuffer の hash と転送元を一致させる

対象: VulkanGlTexture.java:589–607 / 1362–1366。

hash は rgba.get(i) の絶対 index 0 起点、memCopy は memAddress(rgba) の現在 position 起点。
non-zero position の direct buffer では異なる bytes を hash して転送するため、誤った duplicate skip を起こし得る。
remaining が width*height*4 より短くても、hash のループだけ短くなり、native memCopy は full byte 数を読む。

現在の内部 caller が position=0 の十分な buffer を渡すケースまで壊れているとは言わない。
入口で寸法・乗算 overflow・direct buffer・remaining を検査し、slice/duplicate により hash と copy の対象範囲を同じにする。

## F11 — GPU 共通化の受入要件を明示する

対象: VulkanContext.java、GllessFrameTarget.java:185–198、VulkanTerrainPipeline.java:85 / 896。

## F13 — hot path とベンチの測定条件

対象: VulkanTerrainGpuBackend.java:6539–6580、VulkanGlTexture.uploadFromGlTexture、docs/plan.md §0.111。

lightmap refresh countdown=1 で uploadFromGlTexture を毎フレーム呼ぶ。bridge では GL readback を hash の重複判定より前に実行するため、upload skip でも読戻しコストは残る。

GL-less の同じ関数は stub が捕捉した CPU pixels を読み、実 GL readback は必要としない。この二つを混同しない。

F04 の announcement-only 正しさを確かめた後、CPU 供給・generation で閉じる経路へ整理し、実 call site ごとの回数・時間を記録する。
現 benchmark の Celeritas baseline は約16 ms cap、Celtium は uncapped。軽い世界の 6.84 ms 対16.05 ms を、そのまま一般的な倍率として宣伝しない。
最終 native 経路では同一 GPU・camera・world・settings・cap/vsync・温度条件で、p50/p95/p99、GPU時間、chunk更新、allocation/readback を比較する。正しさの修正をこの測定で止めない。

## 確認できた良い点・除外した疑い

- 通常 shader は修正後の実 jar に戻っている。白固定で暗さを隠した jar を受入 artifact として使っている証拠はなかった。
- 正常 terrain_solid_vanilla.vert.spv は 7804 byte、SHA-256 **9ee25c4e5eca40d8387d82e7340c1a0d791df9a7e9d721d0fb877627950a4b5e**。
- terrain_solid.frag.spv は 8864 byte、SHA-256 **bc1e741db9983d3209379d6257f761515e1cdab74dd7a5f0071cfe6bf70c3fb5**。
- 検査した本体 jar の class major は {52:609,65:80,51:1,46:111}。65 より上はなく、release 21 の bytecode 上限は守っている。JDK21 でゲーム全体を新たに実行した証明ではない。
- 同一 jar の AMD/Intel GL-less は実選択ログで確認できた。run 名だけで数えたものは除外した。
- 実 swapchain 提示、通常 shader、region-per-slot readback、post の実発火には進展がある。モデル 2 list という古い数字を、38 list の outline2 の全状態へ当てはめない。
- GL-less の matrixMirrorDelta=0 は独立比較ではない。frame mean や色数だけで全画面の正しさを断定しない。
- GLSL の vertex-stage texture() 一般を「必ず未定義」とする説明は採用しない。[公式 GLSL 説明](https://github.khronos.org/Vulkan-Site/glsl/latest/chapters/builtinfunctions.html) は非 fragment stage の mipmapped lookup に base texture を使用すると説明する。今回の explicit LOD 変更だけで根因を説明できた証拠もない。
- allocateImage の例外処理で image を破棄する前に未使用の memory を free する順番だけを、確定 VUID として数えない。[vkFreeMemory](https://docs.vulkan.org/refpages/latest/refpages/source/vkFreeMemory.html) は、以後その resource を使用しない場合の bound memory の free を許している。
- GUI を隠す fixture、意図的な checkerboard world、camera 差、post 実験の特殊な背景を通常 Minecraft の不具合と混同しない。
