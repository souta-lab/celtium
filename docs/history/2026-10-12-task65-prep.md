## 1. The baseline

`scripts/cpu-contract/verify_line_baseline.txt` - the `CELTIUM_VERIFY` line from
`.celtium-work/runtime/r172b-panorama-menu/validation-console.log`, verbatim:

* **15,824 characters**, 758 space-separated tokens, 535 of them `key=value`;
* sha256 `f769f39ba35196fa461847ef2c245e3ffd568bf69563360e62444c6a0aefb2e2`.

The line carries duplicate keys (`frameId=` appears twice), which is why the comparison is positional: a dictionary
would keep the last occurrence and hide a change in the first - measured while testing the tool, where a perturbed

## 2. What `verificationSummary()` reads

The block is `verificationSummary()` (`VulkanTerrainGpuBackend.java:7869-8318`, 450 lines) plus seven helpers it
calls: `alphaReferenceValueSummary` (`7853-7867`), `alphaSelectorSummary` (`7835-7850`), `flushEntrySummary`
(`1221-1233`), `frameTargetPairSummary` (`4109-4112`), `offTargetSummary` (`4090-4097`), `offerStageSummary`
(`2341-2349`), `unflushedTargetDropSummary` (`1208-1218`) - about 540 lines together.

It references **289 distinct fields** and **4 methods**:

| class | count | what it means for the extraction |
|---|---|---|
| fields read, `private` today | **287** | stay in the backend (they have writers everywhere); the moved code must be able to read them |
| fields read, already non-private | 2 | - |
| methods read, referenced only inside the block | 0 | nothing to move for them |
| methods read, also referenced outside | 4 | `celtium$arenaUploadCount`, `celtium$arenaUploadedBytes`, `descriptorSetCensus`, `offTargetSummary` |

The writers stay where they are: of the 289 fields, 253 are assigned directly elsewhere in the file and 16 more are
mutated through a collection or an array (`this.acceptedByFormat[i]++`, `this.immediateGroups.add(...)`); moving any
of them would touch hundreds of call sites. The Lead's contract #2 and this census agree.

## 3. Design: `BackendReport` reads the backend's fields, nothing moves but the formatting

```java
// celtium-vulkan/src/main/java/org/soutalab/celtium/vulkan/BackendReport.java
final class BackendReport {                       // same package as the backend
    private final VulkanTerrainGpuBackend backend;
    BackendReport(VulkanTerrainGpuBackend backend) { this.backend = backend; }
    String verificationSummary() { ...moved body, `this.` -> `backend.`... }
    // + the seven helpers, describe(), record()
}
```

and in the backend, one line per public entry point:

```java
public String verificationSummary() { return new BackendReport(this).verificationSummary(); }
```

Mechanics:

1. **Widen the 287 fields to package-private** (drop the `private` keyword). No field moves, no writer changes, no
   accessor is written: the moved code reads `backend.foo` directly. This is the only wide edit, and it is one token
   per declaration line.
2. **Move the eight methods verbatim**, replacing `this.` with `backend.` - mechanical, so the string cannot change by
   construction.
3. The four shared methods become package-private (or keep a one-line delegate in the backend for
   `offTargetSummary`, which is called from elsewhere too).
4. `verificationSummary()`, `describe()` and `record()` keep their signatures in the backend as delegates, so no
   caller anywhere changes.

Why not the alternatives:

* **Snapshot record**: ~289 components, and the backend would grow a ~290-line construction site, so the file shrinks
  by far less than it gains in readability; the moved body would be rewritten field by field instead of renamed.
* **289 accessors**: keeps the fields `private`, but adds ~290 lines to the very file the split exists to shrink, and
  289 more lines for the next editor to conflict with.

The design is reverse-engineered from the acceptance: nothing may change in the output, so the safest extraction is
the one where the formatting code is *moved* rather than rewritten, and the data stays where its writers are.

## 4. The acceptance command

```sh
# after task-64 lands and the extraction is in: same leg, same flags, then
python3 scripts/cpu-contract/verify_line_check.py --run .celtium-work/runtime/<same-leg-dir>
```

* exit 0 and `IDENTICAL` is the acceptance (byte-for-byte, 15,824 characters);
* on a difference it prints the first offset and **every** differing token with its key and both values, plus
  `OCCURRENCES` lines for keys whose occurrence count changed, so "which field, what against what" is answered
  without reading the 15 kB line;
* `--structural` tolerates the listed volatile keys (`frameId`, `lastDraw`, `*Millis`, `*Count`, ...) and is a
  *diagnostic* for a re-take whose counters moved - it is not the acceptance and says so in its verdict;
* `--save --from-log FILE` re-baselines deliberately.

Measured with the tool as it stands: identical line `exit 0`; a perturbed `skipReason`/`immediateState` `exit 1` with
both tokens named; a perturbed `frameId` `exit 1` in exact mode and `exit 0` under `--structural` with
`STRUCTURALLY-EQUAL (volatile tokens differ: frameId)`; a *different* leg (`r174-panorama-menu-dump`, 15,826 chars)
`exit 1` with 213 changed tokens - i.e. the tool tells "another run" apart from "the same leg re-taken".
