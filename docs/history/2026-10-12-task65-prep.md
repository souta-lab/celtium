## 3. Design: `BackendReport` reads the backend's fields, nothing moves but the formatting

> **PROVISIONAL - corrected by `docs/refactoring-plan.md` §6.1 (`c85b753fd`).** This shape is a *mechanical format
> move for R1c*, not a permanent responsibility boundary. The plan's own words: "これを恒久的な責任境界には採用しない
> … 単に `BackendReport` が巨大backendを読み、`CopyHost` がすべてのfieldを公開する状態で終了しない", and §9.2 makes
> that a non-landing condition: a new class that depends on every field of the old backend, with the writers left in the
> old class and no removal destination, must not land. The permanent shape is per-domain statistics moved *with* their
> domain (terrain / immediate / texture / target / submission / model / font) and a report that combines their
> read-only snapshots - §3.1 is the schedule for that, and the widening below is the minimum that lets R1c keep the
> `CELTIUM_VERIFY` string byte-identical while R2-R7 do the real separation.
>
> The comment this file will carry when it is created, verbatim:
>
> ```java
> /**
>  * The verification summary's formatting, moved out of the backend so the file can be split.
>  * <p>
>  * PROVISIONAL, per docs/refactoring-plan.md §6.1: this class reads the backend's fields directly (package-private,
>  * widened only for this move) and owns none of them. It is a format move for R1c, not a responsibility boundary.
>  * The permanent owners are the per-domain statistics of R2-R7 (see the table in
>  * docs/history/2026-10-12-task65-prep.md §3.1); when a domain moves, its fields and their counters move with it and
>  * the widening recorded for that domain is removed. Do not add fields here, do not write to the backend, and do not
>  * widen another field without recording its user and its R2-R7 destination.
>  * <p>
>  * Read-only by contract: every field it touches is read, never assigned, and a writer added from another renderer
>  * would break the ownership this move is only borrowing.
>  */
> ```


```java
// celtium-vulkan/src/main/java/org/soutalab/celtium/vulkan/BackendReport.java
final class BackendReport {                       // same package as the backend
    private final VulkanTerrainGpuBackend backend;
    BackendReport(VulkanTerrainGpuBackend backend) { this.backend = backend; }
    String verificationSummary() { ...moved body, `this.` -> `backend.`... }
    // + the seven helpers, describe(), record()
}
```

and in the backend, one line per public entry point:

```java
public String verificationSummary() { return new BackendReport(this).verificationSummary(); }
```

Mechanics:

1. **Widen the 287 fields to package-private** (drop the `private` keyword). No field moves, no writer changes, no
   accessor is written: the moved code reads `backend.foo` directly. This is the only wide edit, and it is one token
   per declaration line.
2. **Move the eight methods verbatim**, replacing `this.` with `backend.` - mechanical, so the string cannot change by
   construction.
3. The four shared methods become package-private (or keep a one-line delegate in the backend for
   `offTargetSummary`, which is called from elsewhere too).
4. `verificationSummary()`, `describe()` and `record()` keep their signatures in the backend as delegates, so no
   caller anywhere changes.

Why not the alternatives:

* **Snapshot record**: ~289 components, and the backend would grow a ~290-line construction site, so the file shrinks
  by far less than it gains in readability; the moved body would be rewritten field by field instead of renamed.
* **289 accessors**: keeps the fields `private`, but adds ~290 lines to the very file the split exists to shrink, and
  289 more lines for the next editor to conflict with.

The design is reverse-engineered from the acceptance: nothing may change in the output, so the safest extraction is
the one where the formatting code is *moved* rather than rewritten, and the data stays where its writers are.

### 3.1 Where the 289 fields go in R2-R7 (the provisional widening's removal destinations)

The report block reads 289 fields. Grouped by the domain that will own them (classified by name and use; the counts
are exact, the examples are the first of each group):

| domain (permanent owner) | R stage | fields | examples | what removes the widening |
|---|---|---|---|---|
| terrain - `TerrainRenderer` region resources, upload, ordered draw | **R4** | 26 | `regionUploadFailures`, `lastRegionUploadFailure`, `terrainIndirectDraws`, `terrainDirectEquivalentDraws`, `frameArena`, `sectionsLeftUnbuilt`, `lastSectionsDrawn` | the fields move with the terrain implementation; the report reads a terrain statistics snapshot |
| immediate - `ImmediateRenderer` accept / queue / record | **R3b** | 115 | `flushCount`, `actualFlushNanos`, `groupCreateCount`, `alphaSelectorCounts`, `blendPairs`, `captureStateNanos`, `fastMergedBatches` | the largest group; it moves with the accept/queue/record extraction, and the report takes its snapshot |
| texture - mirrors, samplers, published textures, descriptor census | **R2** (statistics), texture domain later | 29 | `bindTextureCalls`, `bindShortCircuits`, `lightmapCoordEnables`, `publishedFrameTexturesCreated`, `animatedImageFills`, `partialMirrorsCompleted` | per-domain statistics object in R2; the texture domain keeps writing its own counters |
| target - framebuffer identity, pairs, clears, post | **R5** | 31 | `chainPairClears`, `offTargetDrawn`, `gameClearsRoutedToPairs`, `frameFenceWaitMillis`, `frameId`, `acceptedForOtherTargets` | `RenderTargetRegistry` / `VanillaPostProcessor` take the state; the report reads their snapshot |
| submission - slot, fence, present, retirement | **R6** | 18 | `submitSequence`, `completedSubmitSequence`, `idleWaits`, `signalOnlySubmissions`, `slotReuseWaits`, `commandBuffer`, `gpuStalled` | `FrameSubmissionScheduler` and the device retirement manager take them |
| model - geometry cache and its refusals | **R3a** | 6 | `modelDraws`, `modelDrawRefusals`, `modelLastRefusal`, `mirroredModelViewDelta` | `ModelGeometryCache` takes them |
| font - glyph runs and separators | **R3b** | 3 | `fontBatchesStarted`, `fontQuadsAppended`, `fontStripSeparators` | `FontBatch` takes them |
| report/other - format histograms, projection and matrix diagnostics, driver/device lines | **R2** | 61 | `acceptedByFormat`, `drawnByFormat`, `derivedProjectionDelta`, `gluPerspectiveShapes`, `celtium$arenaUploadedBytes` | these stay report-side by design: they are counters the report owns or reads from the mirror, not a domain's state |

Rules this table is the record of:

* **Read-only**: `BackendReport` never assigns a field; the writers stay in the backend for R1c and move with their
  domain in R2-R7. No other renderer may write a field this class reads.
* **No new accessors**: the widening is `private` -> package-private on the fields the report reads, and nothing else -
  not 289 getters, not a snapshot record (both rejected in §3 and by the plan).
* **Every widening has a destination**: the table above is that record; a field widened without a row is a defect in
  this move, and §9.2 is why.

### 3.2 The baseline: pre-merge kept, post-merge is the acceptance

`verify_line_baseline.txt` is the pre-merge `r172b-panorama-menu` line (15,824 chars, 758 tokens, sha256
`f769f39b…`). It is kept as the record of what the line looked like before `c85b753fd`.

`verify_line_baseline_postmerge.txt` is the **acceptance baseline**: the same leg re-taken on the merged tree
(`main = c85b753fd`, jar `cbd4c46c6bafb29f5332e27c16527889`, the same nine `-Dceltium` flags as `r172b-panorama-menu`:
glless, presentReadback, validation=false, enqAll, enqFormat=2, drawSiteLines=8, menuHoldTicks=60, dumpPresentedImage,
validation=true; AMD RX 6400; `fixtureStatus=PASSED`, `validationClean=true`, `validationMessageCount=0`). It is
**16,114 chars, 779 tokens (552 `key=value`), sha256 `24bd28fd666cb1325df87989a0befbec0d51c1ac9253e5b3a8dcbefe5a926abe`**,
and the tool reports `IDENTICAL` against it (exit 0).

Measured difference between the two, which is why the post-merge one is the acceptance: **726 tokens differ, 21 tokens
were added and 17 more `key=value` occurrences appeared** (758 -> 779 tokens, 535 -> 552 pairs), the first difference
at offset 62. The merge added counters (the publication family among them) and the run itself differs, so a diff taken
against the pre-merge line would fail for reasons the extraction did not cause.

**Which is the acceptance**: `verify_line_baseline_postmerge.txt`. The extraction's diff is taken against it, on a leg
re-taken with those same flags.

## 4. The acceptance command

```sh
# after task-64 lands and the extraction is in: same leg, same flags, then
python3 scripts/cpu-contract/verify_line_check.py --run .celtium-work/runtime/<same-leg-dir>
```

* exit 0 and `IDENTICAL` is the acceptance (byte-for-byte, 15,824 characters);
* on a difference it prints the first offset and **every** differing token with its key and both values, plus
  `OCCURRENCES` lines for keys whose occurrence count changed, so "which field, what against what" is answered
  without reading the 15 kB line;
* `--structural` tolerates the listed volatile keys (`frameId`, `lastDraw`, `*Millis`, `*Count`, ...) and is a
  *diagnostic* for a re-take whose counters moved - it is not the acceptance and says so in its verdict;
* `--save --from-log FILE` re-baselines deliberately.

Measured with the tool as it stands: identical line `exit 0`; a perturbed `skipReason`/`immediateState` `exit 1` with
both tokens named; a perturbed `frameId` `exit 1` in exact mode and `exit 0` under `--structural` with
`STRUCTURALLY-EQUAL (volatile tokens differ: frameId)`; a *different* leg (`r174-panorama-menu-dump`, 15,826 chars)
`exit 1` with 213 changed tokens - i.e. the tool tells "another run" apart from "the same leg re-taken".
