## 1. 判定

**Celeritasの最適化は相当部分が残っている。だが、Vulkan転送・draw submissionまで元の効率を維持している、とは言えない。** common/forge122のupstream既存Javaファイル359件をgit objectで比較し、341件が同一、17件が変更、1件が削除だった。チャンク生成、可視判定、translucent sorting、BatchAssemblerは実際のVulkan経路でも使われている。一方、転送はsegmentごとのsubmitと前後のqueue idle、地形の最終drawはcommandごとのvkCmdDrawIndexedになっている。

**現状は「Minecraftの意味を扱うnative rendererに、限定的なGL APIの意味変換が併存」している。完全なZink型変換器ではない。** 監査中のtask-50ではstubのglMultMatrixf/dへ無条件の意味を加える試行があり、汎用化と二重適用を指摘した。**配送前の19:16追跡では、ForgeHooksClientMixinという公開Forge入口をownerにする修正へ進み、raw matrixの無条件適用は撤回されていた。** このsource改善を反映する。既存glDrawArrays/raw-pointer/glCopyの低い境界は引き続き監査対象である。

**実プレイ報告は、完成扱いにできない具体的な受入課題である。** GUIブロックアイコンの平坦化・枠いっぱいの表示は保存画像でも直接確認した。原典にはForgeの共通camera transformがGlStateManagerを迂回する経路があり、固定点のCeltiumはその行列を反映していない。剣・GROUND・GUIを別々の定数調整で直す状況ではない。

前進も明確にある。

- 通常プレイの大量ログは、固定点ですでに既定OFFと上限を設けた修正が入った。
- 最新のvideo settings画像は、参照Celeritasの同画面とRGB差が最大1だった。Cloudsの変更・保存・再表示・元の値への復元も記録されている。

**フルVKの実機経路は成立している。vanilla全画面・全描画familyの正しさ、通常プレイの滑らかさ、主要mod、広いGPU能力範囲の完成は、まだ成立していない。** 描画要素の数やtask完了数からVK率・完成率を作らない。

## 3. Celeritas由来の最適化を残しているか

### 3.1 全件比較の結果

対象はupstreamに存在する `common/src/main/java/` と `forge122/src/main/java/` のJavaファイルである。新設Vulkan module、リソース、他Minecraft版のmodule、docsは、この359件の分母に含まれない。

| 比較 | 件数 |
|---|---:|
| upstream既存Java | 359 |
| 同一git object | 341 |
| 変更 | 17 |
| 削除 | 1 |
| 選択したrender/gl等の既存203件 | 同一193、変更10 |

削除されたのは `CeleritasLwjgl3ifyCompat.java`。Cleanroom専用化と整合する。最適化algorithmを大量に置き換えた証拠ではない。ファイル同一率を、性能維持率・動作互換率・完成率へ読み替えない。

### 3.2 algorithmだけでなく実行経路も確認した

| 最適化・機構 | 継承の確認 | Vulkan実行経路・残る点 |
|---|---|---|
| 並列chunk build / executor | ChunkBuilder等が原版と同一 | RenderSectionManager constructorからChunkBuilderを使い続ける |
| world slice / cloned world data | 既存Java比較とmeshing経路を確認 | 元のslice・section単位処理・Forge render layerを使う |
| block/model meshing | 共通mesh生成は継承 | Forge fast rendererの既定値は変わった。下記3.3 |
| face / visibility culling | OcclusionCuller、frustum等を継承 | RenderSectionManagerのrender listsをnative backendへ渡す |
| render-list組立 | 継承 | backend.renderが既存listsを受ける |
| translucent sorting | PartitionTree、sort task等を継承 | sectionのsort outputとindex uploadをnative側へ流す |
| region / section storage | dataとsegmentのinterface化が中心 | GLのarena実装が残っていてもnative legはVulkan arenaを使う |
| compact vertices | CompactChunkVertexのencodeを維持 | 24B compactと32B vanilla-likeをnative layoutへ渡す。強制flagと通常optionを区別 |
| BatchAssembler / batch cache | 原版と同一、native factoryへ差替 | createCachedBatchをnative drawでも呼ぶ |
| 多drawのGPU submission | CPU側batchは残る | GLのmultiDrawElementsBaseVertex相当が、そのまま同数の少ないVulkan呼出しになったわけではない |
| mapped staging / transfer合流 | 原版GL実装自体は残る | native arenaは別実装で、原版のcopy合流・fence retirementを継承していない |
| 再upload / 動的更新 | section updateとsort invalidationは残る | 実uploadの待ち、buffer growth、texture更新のコストはnative側で別途確認が必要 |

主要call pathは次の通り。

```text
SimpleWorldRenderer.drawChunkLayer
  -> RenderSectionManager.renderLayer
  -> 選択されたTerrainGpuBackend.render
  -> 既存ChunkRenderLists + SectionRenderDataStorage
  -> BatchAssembler.createCachedBatch
  -> VulkanMultiDrawBatchのcommand
  -> vkCmdDrawIndexed
```

確認箇所: RenderSectionManager constructor付近156–169、renderLayer585–591、uploadChunks697以降、uploadMeshes731、sorting769–817、ChunkBuilderSortTask953。VulkanTerrainGpuBackendではfactory設定426、BatchAssembler使用6896、draw loop6993（18:32固定点の行番号）。

### 3.3 Celeritasのfast block rendererは「同じ既定値」のままではない

`ChunkBuilderMeshingTask.USE_NEW_BLOCK_RENDERER` は、upstreamではdeobf環境またはopt-in propertyで有効だった。Celtiumではpropertyが明示falseでなければ有効で、production既定が変わっている。

実際の分岐も読んだ。

- MODELかつfast renderer有効なら `VintageBlockRenderer.renderBlock`。
- それ以外は `BlockRendererDispatcher.renderBlock`。
- Forgeのrender layer設定、TESR収集、Fluidloggedの別経路、occlusion dataの作成は残る。

この変更はfast pathの利用を増やす。一方、dispatcherにMixinするmodの挙動まで同じとは限らない。公開IBakedModelのデータ経路を保つことと、dispatcher hookをすべて通ることを分ける。主要modのblock/model受入で、この既定変更を記録する。

`VintageBlockRenderer` の主な差分は既定OFFのbrightness diagnostics、`VintageDiffuseProvider` は既定OFFのnoShade実験flagだった。これらのflagを有効にした画質を製品の正しさとして受け入れない。

### 3.4 C03 — native転送が元の効率を削っている（P1）

sourceで以下の連鎖を確認した。

```text
VulkanArena.upload(Collection<Upload>)
  -> 各uploadのVulkanBuffer.write
  -> VulkanContext.uploadToBuffer
  -> recordStagingCopy
  -> beginCommands: vkQueueWaitIdle
  -> vkCmdCopyBuffer
  -> endCommands: vkQueueSubmit + vkQueueWaitIdle
```

固定点のVulkanArena231–258、VulkanBuffer84、VulkanContext607–641/1288–1294、beginCommands322、endCommands565。

**N件の非空uploadを処理すると、この経路はN回のone-shot submissionと、その前後のqueue idleを呼び得る。** staging容量拡張等の追加待ちは別にある。これは動的なchunk更新の際にCPUとGPUの並行を減らす。通常プレイのラグ全体をこの箇所だけのせいと断定はしないが、明確な性能上の構造である。

upstreamの `MappedStagingBuffer` はhost mapped ringへcopyをenqueueし、flushでtransferを合流し、fenced regionで寿命を追っている。native側にその性質を移す余地がある。

修正方針は、Minecraftのsection upload batchを一つの転送単位として扱い、staging rangeをfenceでretireすること。メモリ寿命を確保せず待ちだけ消さない。大量の個別GL APIを実装する必要はない。

受入: 同一scene・同一描画量で、upload数/bytes、submit数、queue-idle呼出し数、CPU time、p95/p99、更新完了までの時間を比較する。静止sceneだけのFPSでこの修正を判定しない。

### 3.5 C04 — native側のfinal multi-drawは未同等（P2）

`VulkanMultiDrawBatch` は原版BatchAssemblerのcommandを保持し、backendはそれをfor loopで `vkCmdDrawIndexed` にしている。native地形経路で `vkCmdDrawIndexedIndirect` を使う実装は今回のsource検索で確認できなかった。

CPU側のsection合流・batch cacheを捨ててはいない。だがGPU command記録/API呼出しの削減まで同じではない。correctness後にdraw indirect等を評価する価値はある。追加featureがないGPUでは現在のindexed triangle経路を維持し、必須能力を増やさない。

**mesh shaderは本監査のsourceでは使われていない。** 速さやGPU対応をmesh shader対応の有無に結び付けない。

## 4. 汎用GL→VK変換器を作っていないか

### 4.1 分類

Mesa ZinkはOpenGLをVulkan上に実装するdriverである。Celtiumの現在のsourceには任意GLSL/programのcompile・link・uniform・全draw modeをVulkanへ実行する仕組みはない。一方で「GLを一切意味変換していない」という説明も成立しない。

| 入口・機構 | 現在の性質 | 方針との判定 |
|---|---|---|
| Celeritas terrain backend | section/region/pass/render listをnative drawへ | Minecraft/Celeritas固有の移植 |
| WorldVertexBufferUploader | BufferBuilderの既知formatをnativeへ | 公開ゲームAPIの互換入口 |
| TexturedQuad / ModelRenderer capture | model quadとmesh cacheをnativeへ | Minecraft modelの共通入口 |
| GlStateManager mirror | game stateをVulkan stateへ | ゲームAPIの互換入口。単一ownerにする |
| FontRenderer glyph window | 既知の文字描画期間だけcapture | scoped adapter。汎用glBegin/glEnd実装ではない |
| named vanilla post chain | 7program名に対応するCeltium shaderを使用 | Minecraftの意味を知るnative pass |
| stub texture/buffer/FBO name保持 | GL upload等をshadow storageへ | すでに限定的なGL API意味変換 |
| stub glDrawArrays decode | format/modeを見てraw callerを受ける | game ownerに限定されていない。境界が低い |
| glCopyTex系 | owned imageから同期readback→CPU texture mirror | GL APIによるadapter。panoramaを固有passへ移す余地 |
| glMultMatrixf/d | 19:00は任意callをnative適用、19:16はarrival-onlyへ是正 | Forge入口をownerにするsource改善。新jarの実画面受入待ち |
| arbitrary mod shader/compute等 | 実装なし、一部入口はno-op | 汎用変換器完成ではない。互換成功と報告できない |

stubのファイルサイズ自体を汎用化の証拠にはしない。入口の制約と意味のownerを基準に判断する。

### 4.2 glDrawArraysはcaller allowlistではない

固定点のglDrawArrays2742以降では、GL_QUADS、position float3、既知stride/enable mask等の条件を確認する。VBOならstub buffer store、client pointerならBufferBuilderのowned publicationを使う。

しかしowned publicationがなくても、`/proc/self/maps`でreadable mappingと判定されればraw pointerを受ける経路が残っている。**既知formatに一致する任意modの直接GL呼出しも通り得る。** callsite censusは診断用で、acceptanceのallowlistではない。

この経路は単なるGL関数アドレスのダミーではなく、低い層の実描画adapterである。未知callerへ広げて「これで全modが動く」としない。Minecraft/Forgeのownerがgeometryと寿命を渡す入口へ寄せ、未対応callerは対象と理由を診断する。

また/proc mappingはLinuxの仕組みで、allocation owner・bufferの寿命・他OSの動作保証にはならない。owned buffer公開を主経路にした改善は評価するが、fallbackまでportableとしない。

### 4.3 任意shaderは動かない。成功statusとの不一致もある（C11、P2）

固定点では `glShaderSource / glCompileShader / glLinkProgram` がno-opで、`glUseProgram` はIDの記録。`glGetShaderiv / glGetProgramiv` はCOMPILE/LINK/VALIDATEのstatusに1を返す。compile成功statusが返っても、対応するmod shaderがVulkanで実行された証拠にはならない。

`glDrawElements`、instanced/indirect draw、compute等の一般実装も確認できない。glCallListのname保持と、CeltiumのModelRenderer固有mesh replayは別物である。

vanilla post側は `invert / blit / blur / bits / entity_outline / color_convolve / spider` の7programに既知SPIR-Vを割り当てる。これは arbitrary GLSL translatorではない。

必要な対策は、bootstrap用façadeとmodが実際に利用できる能力を分けること。未対応shaderが使われたときは対象を明示し、shader adapterの範囲を狭くする。全statusを一斉に変えて起動を壊すのではなく、ゲームが必要とする初期化とnative drawの契約を分けてレビューする。

### 4.4 境界を維持する具体的な条件

- まずMinecraft/Forgeの公開入口でstate/model/geometryを受ける。
- 共通VK allocator、buffer、descriptor、pipelineの再利用は継続する。
- 既存modの同じゲームAPI利用を共通経路で動かす。item/entityごとの手作業を増やさない。
- 直接GLが残る場合は、caller・layout・target・lifetimeの範囲を明記したadapterにする。
- 新しいGL関数を一つ増やす前に、上位のForge/game API一箇所で解消できないか確認する。
- 任意GLSL、display list全体、あらゆるglGet、全GL stateの再現を完成条件に入れない。
- GL-lessで拒否された描画を「GL fallback」と呼ばない。そのwindowにはGL contextがない。
- 比較は原版CeleritasとCeltium GL-lessを基本にし、bridgeの維持を製品互換性の逃げ道にしない。

## 6. C01 — item transform familyの共通欠落（P1）

### 6.1 原典で確認したこと

build生成のForge `ForgeHooksClient.java` 425–455:

```text
handleCameraTransforms(model, TransformType, leftHandHackery)
  -> model.handlePerspective(cameraTransformType)
  -> 左手用flipを含むMatrix4f
  -> multiplyCurrentGlMatrix(matrix)
  -> GL11.glMultMatrix(matrixBuf)
```

Minecraft原典のRenderItem275/312、RenderEntityItem140/155、ItemRendererのfirst-person transform経路も確認した。GUI、held、droppedに同じForge入口がある。

- GlStateManagerMixinは `func_179110_a`、すなわちGlStateManager.multMatrixをmirrorする。
- Forgeのhelperはそのmethodを通らない。
- stubの `glMultMatrixf/d` はNOOP。
- ForgeHooksClient.multiplyCurrentGlMatrixの専用adapterはsource検索で確認できなかった。

GUI画像も、候補ではblockの面がスロットを大きく平坦に埋め、参照は通常の立体iconになる。原典/sourceの欠落は確定した。ユーザーの全症状の実行時因果を同一jarで閉じる受入はまだ必要である。runtime transformerが原典経路を変える可能性は、実callsite/application記録で確認する。

### 6.2 修正の単位

**ForgeHooksClient.multiplyCurrentGlMatrixという共通公開入口で、行列をnative stateに渡す方式を優先評価する。** 既存のVulkanGlStateに行列multiplyの受け側はある。model.handlePerspectiveの返り値、左右flip、column-majorの順序、stack ownerを保つ。

## 7. C02 — matrixの汎用化・二重適用を指摘し、配送前にsource是正

19:00〜19:01のdirty worktreeではtask-50の実装が入り始めた。

- glMultMatrixf/dを `SEM_MULT_MATRIX` に登録。
- glMatrixModeをstub側で記録。
- nonzero pointerから16float、または16doubleを読んで変換。
- current backendがVulkanTerrainGpuBackendなら `backend.multiplyMatrix(matrix)`。
- callerをForge helperに限定するconditionは、この受け側で確認できない。

これはまだbuild/画像受入の済んだfixed artifactではない。次の問題は**作業中のコードレビュー結果**である。

### 7.1 既存mirrorと同じ操作を二度反映し得る

既存の `GlStateManagerMixin` 347–350はHEADで `backend.multiplyMatrix(buffer)` を呼ぶ。そのhookはGL bodyをcancelしていない。Minecraft原典のGlStateManager.multMatrixはその後にGL11の行列multiplyを呼ぶ。

新stubが同じGL bodyにも無条件にapplyすると、同じ行列がmirrorに二回掛かる。**公開GlStateManager.multMatrixを利用する描画経路では、この重複を解消する必要がある。**

GluProjectionMixinもProject.gluPerspectiveのHEADでprojectionをmirrorする。実runtimeではorg.lwjgl.utilとorg.lwjglx.utilのどのクラスが動くかを確かめる必要があり、hookが実際に有効な経路へraw GL multiplyを加えれば同様の二重適用候補になる。原典だけでhook発火を断定せず、effective class/bytecodeとapplication回数を記録する。

また新stubのmatrixModeは診断・保持に使われるが、native mirrorのactive stackと同じであるという保証を、この追加だけで作れるわけではない。任意の直接glMatrixModeまで対応したかのように説明しない。

### 7.2 必要なレビュー

- 一つの操作について意味を適用するownerを一つに固定する。
- Forge APIのadapterなら、GL-lessでGL bodyをどう扱うかを明確にする。
- 既存GlStateManager/GLU hookと新routeを併存させる場合、到着callを二度applyしない規則をsource上で示す。
- `MIRROR_MISSES` はarrival censusであり、単体の欠落counterではない。正しくmirrorされたGL bodyもstubへ到着する。
- arrival/apply数を増やしただけでは正しいprojectionになった証明にならない。matrix値とworld/skyの画像を同じjarで確認する。
- 「itemが直った」ことを理由にraw GL変換の範囲を無制限に広げない。

この点はfull mdの前にDSH leadへqueueで共有した。ユーザーの「汎用変換器は作らない」という方針を維持するためのレビューであり、正しい共通化を妨げるものではない。

### 7.3 配送前の更新：Forge公開入口にownerを移した

19:16〜19:17のHEAD `0357bdf61090de51e0e244ea210ede7caf1dc61d`では、commit `28edeccd6`「One owner for the item camera transform: the Forge entry, not the raw GL call」が入っていた。dirtyのstubも含めて実コードを再取得した。

- 新しいForgeHooksClientMixinが `multiplyCurrentGlMatrix` のHEADでcolumn-majorの16floatを作り、既存backend.multiplyMatrixへ渡す。
- GlStateManagerの既存mirrorは継続。
- raw glMultMatrixのcaseは `celtium$noteMatrixMultiplyArrival` に戻り、nativeへapplyしない。
- 到着counterは残す。任意直接GLの行列を一般実装したという説明にはしない。

**C02の「raw GLと既存mirrorの二重適用」というsource問題は、この採取コードでは是正された。** 旧19:00の問題を現在も無条件適用していると報告しない。Forgeの公開入口で共通化する方向はユーザーの方針と整合する。

Mixin pluginのgetMixinsはcompiled classを走査する方式である。静的JSONにForgeHooksClientMixinの文字列が無いことだけを登録欠落と判定しない。新jarにclassが入り、実targetへ適用されたことを確認する。

残る受入は、実Mixinのregistration/発火、適用したmatrix、最新jarのGUI/GROUND/held左右、projection/skyの不変である。新hookは `require=0`、catch Throwableで黙って継続するため、injection欠落やapply前の例外を成功にしない。backendが存在しない初期phaseと、GL-less描画中の必須入口失敗を区別し、counter/画像に結び付ける。

この配送前のcode bundleは `delivery-source / delivery-manifest.json`、観察JSONは `delivery-followup.json` に保存した。source修正は確認したが、この新ownerを含むjarの独立画像受入は本監査では追加していない。

## 10. C07 — GPU能力とfog/lighting ABI（P1）

### 10.1 208B immediate push constants

VulkanContextのminimumはVulkan1.2。固定点のimmediate payloadは208Bで、line982のcontractも208Bを記録する。immediate pipeline群のrangeも208Bである。

Vulkan1.0〜1.3のguaranteed minimum maxPushConstantsSizeは128B、1.4では256B。**Vulkan1.2対応という条件だけでは208Bを保証できない。** 128B deviceをnamed refusalで落とすことは、説明の改善であってportable描画の完成ではない。

post chainの一部にUBO variantがあることは、immediateの208B問題を直した証拠ではない。immediate側のABIを128B以内のpushとUBO等へ分け、SPIR-V・Java writer・descriptor layoutを同じ単位で変更する。vendor名で分岐しない。

ユーザーの「Vulkan対応GPUで広く動かす」に対して、現行minimumは少なくとも1.2であり、1.0/1.1 driverまでを現在のsourceがサポートしているわけではない。宣伝の「全GPU」と実requirementsを一致させる。

### 10.2 fogとlightingが同じbytesを使う

固定点のbackend2051–2061、fog writer2079–2105、immediate writer9715–9721では、fogとlit payloadが128〜207領域を共有する。lit groupにlightParamsがあると、その領域へlightingを書き、fogを同時に供給できない構造が残る。

これはsourceの契約問題である。ただし古い「inventoryで空が17%暗い/全体48%差」の原因だとした説明は、同じbuild状態の再撮影で支持されなくなった。**B05の存在を理由に、異なる画像の暗さを何でもB05へ帰属させない。**

修正: fogとlightingを別fieldとして共存させ、size/offsetをCPU契約とSPIR-V反映で確認。その後、lit item/modelをfog中に置いたsceneで画像受入する。

### 13.2 wait failureの修正は評価する

VulkanContextのsubmitWithSemaphoresは、timeoutでcommand/fenceを隔離し、device lostはpending/in-useについて完了相当として扱い、その他のfailureは未完了としてquarantineする。endCommandsのqueue waitとcontext teardownのdevice waitにも結果の確認が入った。

この違いはVulkan仕様とも整合する。timeout/OOM等でGPUがまだ参照し得るresourceをfreeしない。修正したため「全ての待ちがbounded」「freezeが解決」とは言えない。queue/device idle APIの待ちは別に残る。

### 13.3 descriptorの旧小容量は増設で改善

ImmediateTexture/Item pipelineはdescriptorPools listを持ち、pool不足時に増設する。旧white fallbackを含む63-key lifetime上限で終わる実装ではなくなった。

一方、pool countには64という上限があり、texture view/generation cacheの旧世代を長時間どう回収するかは別に必要である。reload/skin/dynamic texturesを繰り返すrunでkeys、pool数、live views、retired resourcesを確認する。「無制限」とは書かない。

### 13.4 world teardownとwindow close

windowOwned backendのdeleteはworld resourcesを解放し、device/frame target/swapchainをtitle/loading/次world用に保持する。これはmenuを空にしないための正しい寿命区分である。

worldEpoch stampとqueued group拒否、immediate pipeline cacheの共通releaseも追加されている。sourceの改善を認める。

ただし固定点のbackend full-delete末尾にはcontext.deleteまでの明示的な所有連鎖が確認できなかった。factoryのcontext.deleteは主にcreate失敗のcleanupである。window close/full teardownのowner、surface/swapchain/device/instanceまでの順序をtask-32で閉じる。world離脱のたびにwindow contextを消すことを勧めているのではない。

### 13.5 diagnostics queryが累積する（P2）

VulkanTerrainGpuBackend.diagnostics452以降は、呼ばれるたびに既存ArrayListへdepth/state/timing summaryを追加して返す。summary文字列にはstubTransformCallsの重複もある。

これを現在のF3ラグ原因と断定する呼出し頻度の測定はない。だがqueryが履歴storageを無制限に増やす契約は整理できる。stable configuration、current snapshot、bounded historyを分け、繰り返し照会で説明文が累積しないようにする。
